# Система уведомлений: DocNotifyContext, InboxNotification и ReadState

Документ описывает внутреннее устройство системы уведомлений, в частности, работу и взаимодействие моделей `DocNotifyContext`, `InboxNotification` и `ReadState`. Эти сущности отвечают за управление состоянием прочитанности, маршрутизацией уведомлений и доставкой оповещений пользователям платформы.

## 1. DocNotifyContext

`DocNotifyContext` (контекст уведомлений документа) — это стержневая модель (`Doc` в домене `notification-dnc`), которая связывает конкретного пользователя (`user`) с конкретным бизнес-объектом (`objectId`, `objectClass`). По сути, это "подписка" пользователя на объект, содержащая настройки и хронологию взаимодействия.

### Ключевые поля
- `user` (`AccountUuid`): Пользователь, к которому относится контекст.
- `objectId` / `objectClass`: Ссылка на объект (документ, чат, задача и т.д.).
- `settings.mode`: Режим уведомлений для данного объекта (`'all'` - все, `'mentions'` - только упоминания, `'mute'` - без звука/игнорировать).
- **Временные метки (Timestamps):**
  - `lastView`: Время последнего просмотра объекта пользователем. Обновляется на основе `ReadState`.
  - `lastUpdate`: Время последнего изменения объекта (например, создания нового сообщения).
  - `lastNotify`: Время последнего отправленного уведомления в этом контексте.
  - `lastNotifiedMessage`: Время последнего уведомления о сообщении.

### Роль в системе
Когда происходит транзакция (например, добавление нового комментария в задачу), сервис `notifications` получает все `DocNotifyContext` для участников (collaborators) документа. Основываясь на `settings.mode` и временных метках, система принимает решение: генерировать уведомление или нет, и если да, то обновляет `lastNotify` и/или `lastNotifiedMessage`.

## 2. ReadState

`ReadState` — это модель (наследует `AttachedDoc`), которая хранит состояние прочтения для объекта. Она "прикрепляется" (attachedTo) к основному документу (например, каналу чата или задаче).

### Структура
Представляет собой словарь, где ключом является идентификатор пользователя (`AccountUuid`), а значением — объект `ReadPosition`:
```typescript
interface ReadPosition {
  messageId: Ref<ActivityMessage> // ID сообщения, на котором остановился пользователь
  timestamp: Timestamp            // Время прочтения
}
```

### Роль в системе
Клиентское приложение обновляет `ReadState`, когда пользователь прокручивает чат или открывает документ. 
Когда `services/notifications` обрабатывает транзакцию обновления `ReadState` (в методе `processReadState`), он находит соответствующие `DocNotifyContext` пользователя для этого объекта и синхронизирует поле `lastView`. Это позволяет системе понять, что пользователь уже просмотрел объект, и новые уведомления для прочитанных сообщений генерировать не нужно.

## 3. InboxNotification

`InboxNotification` — это конкретное уведомление (запись во входящих `Inbox`), генерируемое системой для пользователя. Все уведомления во входящих привязываются к своему `DocNotifyContext`.

### Разновидности
Базовый интерфейс расширяется для различных сценариев:
- **`ActivityInboxNotification`**: Уведомления о сообщениях (`ActivityMessage`). Содержит ссылки `attachedTo` и `attachedToClass` на само сообщение.
- **`CommonInboxNotification`**: Универсальное текстовое/размеченное уведомление об изменениях свойств (содержит `header`, `message`, `markup`).
- **`MentionInboxNotification`**: Уведомление об упоминании пользователя (содержит информацию о том, где именно упомянули — `mentionedIn`).
- **`ReactionInboxNotification`**: Уведомления о реакциях на сообщения (содержит `emoji` и ссылку на реакцию `ref`).

### Ключевые поля
- `user`: Кому адресовано уведомление.
- `isViewed`: Флаг прочитанности уведомления в самом Inbox.
- `archived`: Помещено ли в архив.
- `docNotifyContext`: Ссылка на контекст.
- `allowedProviders`: Словарь доступных провайдеров (например, `InboxNotificationProvider`, `PushNotificationProvider`) и типов уведомлений. Определяет, должно ли это уведомление также отправляться в Push или проигрывать звук.

### Жизненный цикл (Workflow)
1. Происходит событие: транзакция (Tx) изменения документа или создания сообщения.
2. `Worker` сервиса нотификаций (файл `services/notifications/src/worker.ts`) перехватывает Tx и передает в `Workspace`.
3. Анализируется Tx. Если это новое сообщение (`processMessage`) или изменение полей (`processTxNotifications`), извлекаются все соавторы документа.
4. Проверяются настройки `DocNotifyContext` (режим `mute` и т.д.).
5. Вычисляется `NotifyResult` (какие провайдеры разрешены).
6. Если уведомление должно быть доставлено, обновляются таймстемпы в `DocNotifyContext`.
7. Создается транзакция на создание `InboxNotification` (например, `ActivityInboxNotification`).
8. В UI пользователь видит `InboxNotification` во входящих. Когда он переходит в объект, обновляется `ReadState`, что, в свою очередь, актуализирует `lastView` в `DocNotifyContext`.
