# Порядок статусов при группировке задач

Как считается порядок групп, когда список или канбан трекера сгруппирован по статусу. Код: `statusOrderComparator` и `mergeStatusOrder` в `plugins/task/src/utils.ts`, точки входа `issueStatusSort` (`plugins/tracker-resources/src/utils.ts`) и `statusSort` (`plugins/task-resources/src/index.ts`). Тесты: `plugins/task/src/__tests__/statusOrder.test.ts`.

## Где применяется

Группировка в списке (`ListCategories.svelte`) получает набор значений атрибута и вызывает `sortCategories` (`plugins/view-resources/src/utils.ts`). Та ищет у класса значения миксин `view.mixin.SortFuncs` и вызывает его функцию:

| Класс статуса | Функция | Кто ставит миксин |
| --- | --- | --- |
| `tracker.class.IssueStatus` (задачи трекера) | `issueStatusSort`, ресурс `tracker.function.IssueStatusSort` | `defineSortAndGrouping` в `models/tracker/src/index.ts` |
| `core.class.Status` (остальные задачи: лиды, кандидаты и т.д.) | `statusSort`, ресурс `task.function.StatusSort` | `models/task/src/index.ts` |

Функция получает список ссылок на статусы, проект (`space`, может отсутствовать во «всех задачах») и дескриптор viewlet'а (список или канбан), сортирует список и возвращает его. Пустые группы в список не попадают, поэтому статус без задач на порядок остальных не влияет.

Дорожки канбана (`swimLaneBy` = статус) идут через ту же функцию: `KanbanView.svelte` вызывает `sortSwimLaneValues` (`plugins/tracker-resources/src/utils.ts`), которая находит у класса значения тот же миксин `view.mixin.SortFuncs` и передаёт дескриптор канбана, поэтому дорожки по статусу упорядочены как колонки канбана. Пустая дорожка всегда первая.

Для `core.class.Status` три ключа ниже применяются только когда выбран тип проекта (`selectedTypeStore`, его выставляет переключатель типов на экранах вроде «Заявки» в подборе). Без выбранного типа `statusSort` работает по старому алгоритму, который в этой работе не менялся: для каждого статуса находится первый тип проекта, где он есть, статусы соответствующего типа задач нанизываются на lexorank в порядке обхода, ключа категории нет.

## Три ключа сортировки

Статусы сравниваются по трём ключам по убыванию приоритета.

### 1. Категория статуса

У каждого статуса есть категория (`Status.category`). Порядок категорий фиксирован константами и не зависит от настроек проекта:

| Где | Порядок | Константа |
| --- | --- | --- |
| Список задач трекера | Active, ToDo, UnStarted, Won, Lost | `listIssueStatusOrder`, `plugins/tracker-resources/src/utils.ts` |
| Канбан трекера | UnStarted, ToDo, Active, Won, Lost | `listIssueKanbanStatusOrder`, там же |
| Остальные задачи (`statusSort`) | UnStarted, ToDo, Active, Won, Lost | `getStatusCategoryOrder()`, `plugins/task/src/utils.ts` |

Список показывает активные задачи первыми, чтобы работа была сверху. Канбан и общая сортировка повторяют порядок колонок на экране «Состояния процесса»: пул задач, не запущенные, активные, завершено/выиграно, завершено/потеряно.

Статус без категории или с категорией вне списка попадает после всех известных категорий.

### 2. Слитый порядок типов задач

Внутри одной категории порядок берётся из настроек типов задач: экран «Состояния процесса» каждого типа, где статусы переставляются перетаскиванием. Порядок хранится в `TaskType.statuses`.

Шаг 2а. Собирается упорядоченный список типов задач (`getOrderedTaskTypes`, `sortTaskTypesByName`):

1. Типы задач текущего проекта, отсортированные по имени. Именно так их показывает экран настроек типа проекта (`ProjectTypeTasksTypeSectionEditor.svelte`). Массив `ProjectType.tasks` хранит порядок создания, который пользователь нигде не видит, поэтому он не используется.
2. Для просмотров без проекта («Все задачи», «Мои задачи») - типы задач всех проектов пользователя, тоже по имени.

Дубликаты убираются, первое вхождение остаётся.

Шаг 2б. Последовательности статусов всех этих типов сливаются в один общий порядок (`mergeStatusOrder`). Правило одно: порядок каждого типа задач сохраняется целиком. Если в типе Issue статус On Hold стоит перед In Progress, то и в общем порядке On Hold раньше, даже если в другом типе In Progress стоит первым.

Технически это топологическая сортировка. Каждая пара соседних статусов в `TaskType.statuses` даёт ребро «предыдущий -> следующий». Затем алгоритм Кана: на каждом шаге берётся статус, у которого не осталось непройденных предшественников. Если таких несколько, побеждает тот, чей ключ меньше. Ключ статуса - пара (индекс первого типа задач, в котором он встречается, позиция в этом типе). Так статусы более раннего типа идут раньше, когда типы друг другу не мешают.

Если типы задач противоречат друг другу (в одном A перед B, в другом B перед A), кандидатов без предшественников нет. Тогда берётся статус с наименьшим ключом среди оставшихся, то есть побеждает порядок более раннего типа. Зацикливания нет.

Статус, которого нет ни в одном из типов, получает ранг после всех известных.

### 3. Имя

Если два статуса неразличимы по первым двум ключам (оба вне типов задач или оба без категории), они сравниваются по имени через `localeCompare`.

## Почему именно так

- **Категория первой.** Пользователь читает список как поток работы: сначала то, что в работе, потом очередь, потом завершённое. Порядок категорий один на все проекты.
- **Порядок типов задач по имени.** Экран настроек сортирует типы по имени. Если бы список использовал `ProjectType.tasks`, порядок зависел бы от того, какой тип создали раньше, и не совпадал бы с тем, что пользователь видит в настройках.
- **Слияние вместо позиции в первом типе.** Шаблон Classic создаёт общие статусы Backlog, Todo, In Progress, Canceled на все типы задач проекта: это один документ, а не копии. Если брать позицию только из первого по имени типа (Feature), In Progress получит позицию первого активного статуса Feature, а On Hold из Issue окажется после него, хотя в Issue он стоит первым. Слияние учитывает все типы сразу.
- **Одинаковые имена не объединяются.** У RAIDRUSH Epic и Issue имеют свои Backlog и Done, это разные документы. В списке будут две группы Backlog и две группы Done, рядом друг с другом. Объединение по имени - отдельная задача, сортировка её не делает.

## Примеры

### RAIDRUSH: у каждого типа свои статусы

Типы задач по имени: Epic, Issue. Настройки:

| Тип | Статусы по порядку |
| --- | --- |
| Epic | Backlog, (not used) Todo, Focus, Done, Canceled |
| Issue | Backlog, Inbox, Reopen, Todo, In Progress, Ready for test, Waiting for, Art ready to insert, In Review, Approved, Done, Canceled |

Общих статусов нет, слияние даёт «все статусы Epic, затем все статусы Issue». Итог в списке по категориям:

| Категория | Порядок |
| --- | --- |
| Active | Focus, In Progress, Ready for test, Waiting for, Art ready to insert, In Review, Approved |
| ToDo | (not used) Todo, Inbox, Reopen, Todo |
| UnStarted | Backlog (Epic), Backlog (Issue) |
| Won | Done (Epic), Done (Issue) |
| Lost | Canceled (Epic), Canceled (Issue) |

До изменения Focus стоял после In Review: позиция бралась из плоского списка `ProjectType.statuses`, собранного в порядке создания типов, а Issue был создан раньше Epic.

### Classic project: общие статусы

Типы задач по имени: Feature, Issue, Task. Backlog, Todo, In Progress, Canceled - один документ на все три типа.

| Тип | Статусы по порядку |
| --- | --- |
| Feature | Backlog, Todo, In Progress, Good, Complete, Canceled |
| Issue | Backlog, Clarify, Todo, On Hold, In Progress, Implemented, Under review, Review completed, Testing, Testing complete, Merged, Deployed, Canceled, Duplicate |
| Task | Backlog, Todo, New state, Won, Lost |

Слияние: Backlog первый у всех. Clarify идёт после Backlog (Issue), Todo после Clarify (Issue), поэтому Todo ждёт Clarify. On Hold идёт после Todo (Issue), а In Progress после On Hold (Issue) и после Todo (Feature), поэтому In Progress ждёт On Hold. Good после In Progress (Feature), Implemented после In Progress (Issue): оба готовы одновременно, Good берётся первым, потому что Feature раньше по имени.

| Категория | Порядок |
| --- | --- |
| Active | On Hold, In Progress, Good, Implemented, Under review, Review completed, Testing, Testing complete, New state |
| ToDo | Todo |
| UnStarted | Backlog, Clarify |
| Won | Complete, Merged, Deployed, Won |
| Lost | Canceled, Duplicate, Lost |

## Граничные случаи

| Ситуация | Поведение |
| --- | --- |
| Статус входит в несколько типов задач | Ранг один, учитываются предшественники из всех типов. Ключ для тай-брейка берётся из первого типа по порядку. |
| Типы задач расходятся в порядке двух статусов | Цикл разрывается в пользу более раннего типа задач. |
| Статус не входит ни в один тип проекта | После всех известных, среди таких по имени. Бывает при смене типа проекта или битых данных. |
| Просмотр без проекта | Порядок типов - типы всех проектов пользователя по имени. Проект не найден - то же самое. |
| Статус без категории | После всех категорий. |
| Дубликат ссылки внутри `TaskType.statuses` | Учитывается первое вхождение. |
| Пустые группы | Не показываются, но на ранг других статусов не влияют: ранг считается по настройкам, а не по видимым группам. |

## Как изменить

- Порядок категорий списка или канбана - константы `listIssueStatusOrder` / `listIssueKanbanStatusOrder` в `plugins/tracker-resources/src/utils.ts`; для общих задач - `getStatusCategoryOrder()` в `plugins/task/src/utils.ts`. Это функция, а не константа: `plugins/task/src/utils.ts` загружается до создания объекта плагина `task` (через реэкспорт `transfer`), и обращение к `task.statusCategory` на уровне модуля падает.
- Порядок типов задач - `getOrderedTaskTypes` / `sortTaskTypesByName` там же. Если появится ручная сортировка типов задач, менять нужно только их и экран настроек.
- Правило слияния - `mergeStatusOrder`.
- Любое изменение фиксируется тестом в `plugins/task/src/__tests__/statusOrder.test.ts`: там воспроизведены обе конфигурации из примеров выше.
