# Архитектура Нотификаций (Новая модель)

В данном документе описывается новая архитектура системы нотификаций, пришедшая на смену старой модели на базе отдельных объектов `InboxNotification`. Основная цель рефакторинга — радикально упростить флоу нотификаций, повысить производительность (за счет уменьшения количества объектов и запросов к БД) и обеспечить более точную работу бейджей и счетчиков непрочитанных сообщений.

## Основная концепция: «Жирный» `DocNotifyContext`

Ранее система строилась на множестве отдельных уведомлений, наследуемых от `InboxNotification` (например, `ActivityInboxNotification`, `MentionInboxNotification`, `ReactionInboxNotification`). Каждое уведомление было отдельным документом в БД.

**Новая архитектура полностью избавляется от наследников `InboxNotification`**. Вместо этого вся информация об уведомлениях консолидируется в едином агрегированном объекте — `DocNotifyContext`. 

Для каждой пары **Пользователь** + **Документ (объект)** создается только один `DocNotifyContext`, который выступает как «fat model» (жирная модель) и служит единым источником правды.

### Разделение ответственностей: `DocNotifyContext` и `ReadState`

Теперь система четко разделяет персональные данные (для инбокса) и глобальные данные (состояние прочтения документа).

**Приватный `DocNotifyContext`** (создается для пары Пользователь + Документ):
Служит исключительно как легковесный индекс для рендера списка Инбокса. Из него удалены все "глобальные" поля, чтобы избежать дублирования данных. В нем хранятся только счетчики и последние уведомления.
- `lastNotify` (Timestamp) — время последнего события (уведомления) для сортировки инбокса по свежести.
- `unreadMessagesCount` (number) — количество новых сообщений.
- `unreadReactionsCount` (number) — количество новых реакций.
- `unreadMentionsCount` (number) — количество новых упоминаний.
- `latestNotifications` (Array<ContextNotification>) — буфер последних N (обычно до 5) уведомлений.
- `reactionNotifications` (Array) — список/массив конкретных новых реакций.
- `mentionNotifications` (Array) — список/массив конкретных новых упоминаний.

*(Поля `lastView`, `lastUpdate` и `lastNotifiedMessage` были удалены, так как они либо дублируют данные из `ReadState`, либо больше не нужны)*

**Публичный `ReadState`** (создается на Документ):
Хранит глобальную информацию о прочтениях, чтобы любой пользователь мог видеть (например, в виде аватарок), кто и до какого момента прочитал документ.
- `latestMessageId` (Ref) — ID последнего сообщения в документе.
- `latestMessageTimestamp` (Timestamp) — глобальное время последнего сообщения/обновления (заменяет `lastUpdate`).
- `[AccountUuid]` (ReadPosition) — мапа, содержащая `timestamp` (заменяет `lastView`) и `messageId` для каждого прочитавшего пользователя.

### `ContextNotification` (Вложенные уведомления)

Вместо того чтобы хранить уведомления как самостоятельные записи в базе, самые свежие и релевантные уведомления хранятся как вложенные объекты типа `ContextNotification` в массиве `latestNotifications` внутри `DocNotifyContext`. 

Это позволяет UI сразу отрисовывать инбокс, делая всего один запрос на загрузку `DocNotifyContext`, избегая join-ов и лишних выборок по `InboxNotification`.

## Жизненный цикл и Триггеры

1. **Генерация события**: При наступлении события (сообщение, упоминание, реакция) триггер на сервере больше не создает `InboxNotification`.
2. **Обновление Context**: Триггер находит (или создает, если его нет) `DocNotifyContext` для пользователя и документа.
3. **Агрегация**: Триггер обновляет счетчики (например, `unreadMessagesCount++`) и добавляет запись в массив `latestNotifications` с помощью операции `$push` (или подобных). При этом старые уведомления вытесняются из массива, чтобы предотвратить бесконечное разрастание документа.
4. **Прочтение (ReadState)**: При открытии документа или ручной пометке "прочитано", обновляется поле `lastView` в `DocNotifyContext`, а массивы `unread*` и счетчики сбрасываются.

## Гибридная модель хранения непрочитанных (Счетчики и Чанки)

Для того чтобы счетчики `unread*` могли плавно уменьшаться по мере скролла чата (без запуска тяжелых `COUNT` запросов в БД) и при этом мы не столкнулись с раздутием массивов у "заброшенных" чатов с тысячами сообщений, применяется **гибридная модель**:

### Структура хранения под капотом
- `unreadMessagesCount` (number) — общий счетчик, который мы отдаем на клиент для бейджиков.
- `reactionNotifications` и `mentionNotifications` — точечные события. Храним объекты-сниппеты, так как их обычно мало. При чтении сервер удаляет прочитанные.
- `unreadMessages` (Array) — единый гетерогенный массив `UnreadMessage[]`. Хранит хронологическую ленту непрочитанных. Свежие сообщения лежат в виде компактных объектов `{ _id, createdOn }`, а старая история спрессована в чанки `{ from, to, count }`.

### Логика работы
1. **Запись:** При получении нового сообщения сервер инкрементит `unreadMessagesCount` и пушит объект `{ _id, createdOn }` в конец `unreadMessages`. Если массив разрастается свыше лимита (например, 1000 элементов), старейшие объекты (например, 10 штук) извлекаются и сворачиваются в один `UnreadMessageChunk`, заменяя удаленные объекты. Благодаря наличию `createdOn` прямо в объекте, база данных не опрашивается при чанкинге.
2. **Чтение (Скролл):** 
   - Клиент скроллит свежие сообщения и шлет батчи прочитанных ID. Сервер делает удаление соответствующих объектов из `unreadMessages` и уменьшает `unreadMessagesCount`.
   - Если клиент скроллит глубокую историю, он шлет свой текущий `timestamp` (или `lastView`). Сервер находит чанки в массиве `unreadMessages`, где `to <= timestamp` (пройденные юзером), удаляет их и уменьшает общий счетчик на `count` удаленных чанков.

### Эвристики оптимизации и ограничения (Sliding Window Compaction)
Для поддержания максимальной скорости и минимального объема данных используются следующие правила:
1. **Жесткий лимит массива (1000 элементов):** Длина `unreadMessages` никогда не превышает 1000. Это гарантирует $O(1)$ по памяти и защищает документ от раздувания BSON-размера даже в заброшенных чатах на 100 000 сообщений.
2. **Нулевая нагрузка на БД при архивации:** Мы намеренно храним объекты `{ _id, createdOn }` вместо простых строк. Когда массив достигает лимита, серверу нужно сформировать чанк из 10 старейших элементов. Благодаря уже сохраненному `createdOn`, сервер просто берет `from` первого элемента и `to` десятого, сворачивает их в чанк `count: 10` в памяти и делает один атомарный апдейт, полностью избегая `SELECT / find` запросов к коллекции `ActivityMessage`.
3. **Плавная деградация (Lazy Chunking):** Чанкинг не запускается до тех пор, пока массив не пробьет лимит в 1000. В 95% активных чатов массив никогда не достигнет этого лимита, а значит система будет работать на максимально точных, поштучных ID без всяких накладных расходов на уплотнение.
4. **Интерполяция прочитанного (Опционально):** При скролле гигантских старых чанков сервер может пропорционально уменьшать `count` чанка в зависимости от таймстемпа пользователя, создавая иллюзию поштучного убывания счетчика для огромных заброшенных историй.

**Результат:** Идеальный UX с плавным поштучным декрементом счетчиков при скролле последних 1000 сообщений, идемпотентность (защита от багов клиента) и нулевые `COUNT` агрегации в БД.

## Удаление из Инбокса и защита от состояния гонки (Race Condition)

При удалении или очистке элемента из Инбокса (когда пользователь нажимает "Удалить") возникает риск состояния гонки: если в момент удаления параллельно генерируется новая нотификация, физическое удаление документа `DocNotifyContext` может привести к безвозвратной потере этого нового уведомления.

Чтобы избежать этого, применяется паттерн **Soft Delete (Скрытие) + Оптимистичная блокировка по Timestamp**:

1. **Отказ от физического удаления**: `DocNotifyContext` является переиспользуемой сущностью. Мы не делаем `deleteOne`, чтобы не тратить ресурсы БД на постоянную деаллокацию и аллокацию документов в активных обсуждениях.
2. **Флаг скрытия**: При удалении из Инбокса мы устанавливаем флаг скрытия (например, `$set: { isHidden: true, hiddenAt: Date.now() }`).
3. **Оптимистичная блокировка (`lastNotify`)**: Чтобы не затереть только что пришедшую нотификацию, клиент **обязан** передавать таймстемп `lastNotify` (или `_id` самого свежего уведомления), который он видит на экране. 
   Запрос на скрытие на сервере должен выглядеть так:
   ```javascript
   db.DocNotifyContext.updateOne(
     { _id: contextId, lastNotify: clientLastNotifyTimestamp },
     { $set: { isHidden: true, hiddenAt: Date.now() } }
   )
   ```
   Если триггер успел добавить новую нотификацию, `lastNotify` в базе изменится. Запрос от пользователя не найдет документ по старому таймстемпу, и скрытие не произойдет. Контекст безопасно останется в Инбоксе с новой нотификацией.
4. **Восстановление**: Любой триггер на новое событие при обновлении `DocNotifyContext` всегда делает `$set: { isHidden: false }`.


## Преимущества новой архитектуры

- **Один источник правды**: Нет рассинхронизации между состоянием прочтения документа и висящими «непрочитанными» `InboxNotification`.
- **Производительность БД**: Значительное сокращение операций записи (create/update/delete) для `InboxNotification`. Теперь происходит один in-place update счетчиков в `DocNotifyContext`.
- **Упрощение клиентского кода (UI)**: Клиенту нужно просто подписаться на изменения своего набора `DocNotifyContext`. Отпадает необходимость фильтровать, склеивать и синхронизировать разные коллекции уведомлений.
