# Postgres: проекция по lookup

Область: [Архитектура платформы](../architecture.md). Смежная заметка: [сортировка по обратному lookup](postgres-reverse-lookup-sort.md).

- Ключи проекции `$lookup.<path>.<field>` режут присоединённый документ до перечисленных полей: `splitProjection` (`foundations/server/packages/postgres/src/utils.ts`) отделяет их от базовой проекции по пути join, `getProjectionsAliases`/`getReverseProjection` в `storage.ts` выбирают только эти колонки, jsonb-ключи через `jsonb_build_object`, исключение jsonb-ключей оператором `data - ARRAY[...]::text[]`. Только lookup-ключи в проекции оставляют базовый документ целым. Режим считается отдельно для базового документа и для каждого пути join: одни нули - исключение, любая `1` - включение, нули при этом игнорируются. Вложенный jsonb-путь (`icon.asset`) берётся по верхнему ключу целиком, исключение такого пути payload не режет: `data->'icon.asset'` дал бы NULL. Путь с миксином (`$lookup.x.contact:mixin:Employee.active`) не разбирается, join остаётся целым.
- В проекции join'а `_id`, `_class` и `space` выбираются всегда, и при включении, и при исключении: `SpaceSecurityMiddleware.filterLookup` проверяет присоединённый документ по `space` (пространство - по `_id`) и без него выкидывает его из `$lookup`; `_id` стоит первой колонкой, по ней `parseLookupColumns` различает join'ы.
- Базовая проекция применяется и в пути с lookup (`parseDocWithProjection` в обоих путях разбора), исключение для базового документа выбирает все колонки домена, кроме перечисленных.
- `Projection<T>` остаётся чистым mapped-типом, lookup-ключи добавлены пересечением только в `FindOptions.projection` (`LookupProjection` в core). Пересечение в самом `Projection<T>` ломает `for (const key in projection)` в адаптерах: ключ становится `string`, а не `Extract<keyof T, string>` (TS7053/TS2322 в postgres и mongo). Значение типизировано `number`, а не `0 | 1`: проекция с вычисляемым ключом (`{ [key]: 1 }` в rank.ts middleware, фильтрах view-resources и contact-resources) выводится как `{[x: string]: number}`.
- Обратный lookup с проекцией собирает строки в форме таблицы (`_id`, `_class`, `space`, `data: {...}`), чтобы `parseDoc` разбирал их тем же путём, что полные.
- `buildOrder` для `$lookup`-ключей добавляет `NULLS LAST` при `DESC` и `NULLS FIRST` при `ASC`: пустая строка join'а (чат без `readState`, комментарий удалённого документа) иначе шла бы первой в `DESC`, так Postgres упорядочивает NULL. Обычные поля не трогаются. Клиентский `resultSort` (`foundations/core/packages/core/src/query.ts`) ставит отсутствующее значение туда же, куда сервер ставит NULL: для `$lookup`-ключей наименьшим (в `DESC` последним), для обычных колонок по умолчанию Postgres (в `DESC` первым, в `ASC` последним); раньше клиент ставил отсутствующее первым всегда. Обычным колонкам явный `NULLS` на сервере не добавляется: индекс `(col DESC)` держит NULL первым, и `NULLS LAST` его не использовал бы.
- Сортировка по полю lookup (`sort: { '$lookup.readState.latestMessageTimestamp': Descending }`) не нуждается в клиентском дубле: LiveQuery после патча присоединённого документа в `handleDocUpdateLookup` вызывает `q.result.sort(...)` по тем же `options.sort`, `getObjectValue` читает путь через `$lookup`. Окно с `limit`, отсортированное по полю join'а (секция activity навигатора, 5 элементов): изменение этого поля у документа, которого в окне нет, LiveQuery не видит; `handleLookupWindowEntry` спрашивает сервер документы запроса по ссылке на изменённый (`findAll(q._class, { ...q.query, [key]: tx.objectId }, { lookup, projection, associations, showArchived })`, один запрос на Tx для всех окон с тем же запросом - ответ лежит в `TxCache.found` батча) и вставляет подошедшие как `handleDocAdd(..., counted = true)`: `total` не меняется, лишнее выталкивается за `limit`. Запрос не идёт, когда окно уже держит документ, ссылающийся на изменённый (его запатчили на месте), когда новое значение не заходит за последний документ окна (`mayEnterWindow`: пробный документ - последний с новым значением - сортируется тем же `resultSort`, ничья не входит), и когда фильтр запроса по `$lookup.<key>.*` не проходит по тому, что Tx сама говорит о документе (`mayMatchLookupFilters`: `_id/_class/space`, `attachedTo/attachedToClass/collection`, поля из `operations`) - навигатор для этого фильтрует `$lookup.readState.attachedToClass`, а Tx состояния несут `attachedTo/attachedToClass`. Поле, которого Tx не называет, считается подходящим. Только прямой lookup верхнего уровня: обратный (`_id: {...}`) и вложенный в окно не поднимаются. Проверка "держит ли окно документ" - по одному документу: если на один присоединённый ссылаются несколько документов запроса и один из них в окне, остальные не поднимутся.
- Проекция join'а должна включать поля, по которым запрос фильтрует и сортирует через `$lookup.<key>.*`, как и базовая проекция включает свои: документ, добавленный вживую, тянет присоединённый документ с проекцией join'а (`getLookupValue`), и без поля фильтра не проходит собственный `match`. Так чат, созданный при открытой странице, не появлялся в навигаторе до перезагрузки, пока проекция была одним `latestMessageTimestamp` без `attachedToClass`. LiveQuery ключи сам не добавляет (`withLiveQueryFields` даёт только `_class/space/modifiedOn`); in-memory тесты этого не ловят, `MemDb` проекцию не применяет.
- Фильтр по полю join'а (`'$lookup.preview.archived': false`) LiveQuery сам не перепроверяет: при транзакции, трогающей такое поле у класса join'а, `handleDocUpdateLookup` перечитывает запрос с сервера (`touchedLookupWays` по ключам `q.query`). Tx, не меняющая полей фильтра (только называющая `attachedToClass` на уровне Tx), перезапроса не вызывает.
- Кеш документов LiveQuery (`Refs`, `foundations/core/packages/query/src/refs.ts`) запрос с проекцией базового документа не кормит; запрос с проекцией только по `$lookup.` кладёт туда целый базовый документ под ключ без lookup, и чтение без lookup получает его с отрезанными `$lookup`/`$associations` (`serve`). Обрезанные join'ы другим запросам не достаются: ключ кеша включает lookup, а `findQuery` сравнивает опции вместе с `projection`. Присоединённые документы `Refs` не кеширует ни для каких запросов.
- Тесты: SQL и разбор строк - `lookupProjection.spec.ts`, `parseLookup.spec.ts`; на реальной базе - `storage.itest.ts` (запуск `npx jest --testMatch '**/storage.itest.ts'`, обычный `testMatch` файлы `*.itest.ts` не берёт); при холодном старте test-containers первый прогон может упасть в `beforeAll` (`clientRef` undefined), повторный проходит.
