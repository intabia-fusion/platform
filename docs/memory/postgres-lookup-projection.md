# Postgres: проекция по lookup

Область: [Архитектура платформы](../architecture.md). Смежная заметка: [сортировка по обратному lookup](postgres-reverse-lookup-sort.md).

- Ключи проекции `$lookup.<path>.<field>` режут присоединённый документ до перечисленных полей: `splitProjection` (`foundations/server/packages/postgres/src/utils.ts`) отделяет их от базовой проекции по пути join, `getProjectionsAliases`/`getReverseProjection` в `storage.ts` выбирают только эти колонки, jsonb-ключи через `jsonb_build_object`, исключение jsonb-ключей оператором `data - ARRAY[...]::text[]`. Только lookup-ключи в проекции оставляют базовый документ целым. Режим считается отдельно для базового документа и для каждого пути join: одни нули - исключение, любая `1` - включение, нули при этом игнорируются. Вложенный jsonb-путь (`icon.asset`) берётся по верхнему ключу целиком, исключение такого пути payload не режет: `data->'icon.asset'` дал бы NULL. Путь с миксином (`$lookup.x.contact:mixin:Employee.active`) не разбирается, join остаётся целым.
- В проекции join'а `_id`, `_class` и `space` выбираются всегда, и при включении, и при исключении: `SpaceSecurityMiddleware.filterLookup` проверяет присоединённый документ по `space` (пространство - по `_id`) и без него выкидывает его из `$lookup`; `_id` стоит первой колонкой, по ней `parseLookupColumns` различает join'ы.
- Базовая проекция применяется и в пути с lookup (`parseDocWithProjection` в обоих путях разбора), исключение для базового документа выбирает все колонки домена, кроме перечисленных.
- `Projection<T>` остаётся чистым mapped-типом, lookup-ключи добавлены пересечением только в `FindOptions.projection` (`LookupProjection` в core). Пересечение в самом `Projection<T>` ломает `for (const key in projection)` в адаптерах: ключ становится `string`, а не `Extract<keyof T, string>` (TS7053/TS2322 в postgres и mongo). Значение типизировано `number`, а не `0 | 1`: проекция с вычисляемым ключом (`{ [key]: 1 }` в rank.ts middleware, фильтрах view-resources и contact-resources) выводится как `{[x: string]: number}`.
- Обратный lookup с проекцией собирает строки в форме таблицы (`_id`, `_class`, `space`, `data: {...}`), чтобы `parseDoc` разбирал их тем же путём, что полные.
- `buildOrder` для `$lookup`-ключей добавляет `NULLS LAST` при `DESC` и `NULLS FIRST` при `ASC`: пустая строка join'а (чат без `readState`, комментарий удалённого документа) иначе шла бы первой в `DESC`, так Postgres упорядочивает NULL. Обычные поля не трогаются.
- Сортировка по полю lookup (`sort: { '$lookup.readState.latestMessageTimestamp': Descending }`) не нуждается в клиентском дубле: LiveQuery после патча присоединённого документа в `handleDocUpdateLookup` вызывает `q.result.sort(...)` по тем же `options.sort`, `getObjectValue` читает путь через `$lookup`.
- Тесты: SQL и разбор строк - `lookupProjection.spec.ts`, `parseLookup.spec.ts`; на реальной базе - `storage.itest.ts` (запуск `npx jest --testMatch '**/storage.itest.ts'`, обычный `testMatch` файлы `*.itest.ts` не берёт); при холодном старте test-containers первый прогон может упасть в `beforeAll` (`clientRef` undefined), повторный проходит.
