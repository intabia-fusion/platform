# Status uniqueness in a project type

Область: [Tracker](../features/tracker.md)

- Before the change, a color-only edit in `CreateStatePopup` (`needUpdate` path) created a new `Status` with the same name and re-pointed the tasks of that task type: a source of duplicates besides the importer.
- `ProjectType.statuses` has one entry per (status, task type) from `calculateStatuses`, but a copy of the FIRST entry with that `_id` is used for all task types; `StatePresenter` also reads the first entry by `_id` only. Color/icon are effectively per project type.
- `createProjectType` / `createStates` on a same-name status in another category creates a new status (an import must not fail halfway); the UI blocks that case.
- Delete decision comes from the server: `deleteProjectTypeStatus` (`plugins/task-resources/src/statusDelete.ts`) calls `getStatusUsage` (`statusUsageDomain`), because a client `findAll` sees only the spaces the user is a member of and no archived ones. Tasks of the project type = sum of `byKind`. Any such task, any project with the status as `defaultIssueStatus` (`projects`) or any workflow that uses it sends the delete through the server merge with `transfer: true`; the plain delete never touched the project default, so `createIssue` would have used a deleted status. Otherwise a confirmation and `removeStatusFromType`.
- Every status task count in the UI goes through `loadStatusTaskCount` (`plugins/task-resources/src/statusMergeApi.ts`): for a Maintainer it is the server usage (`getStatusUsage`, summed by `countStatusTasks` over `byKind`, which covers the task types of the project type), for others and on a failed request the client `findAll` query. The client count misses archived projects and spaces the user is not a member of (`addSecurity`), so the dialogs disagreed: the delete dialog said "Tasks: 1" and the merge confirmation `MergeStatusesDetails` said 0 for a task in an archived project. Users of the helper: `MergeStatusesDetails` (all task types: `MergeStatusesConfirm` merges without `taskTypes`), `DeleteStateConfirmationPopup` (one task type), `CreateStatePopup` (duplicate-name block and rename approval; `save` awaits the count before deciding).
- A workflow uses a status (`loadWorkflowUsage`, `statusUsage.ts`) when it is initial, the `from` or `to` of a transition, or listed in `validators[].props.statuses` of a `SubtaskStatus`/`ParentStatus` rule (`collectRuleStatusIds`). `removeStatusFromType` keeps the `Status` doc when the id has ':', `usage.tasks` (the whole workspace) is above 0, another project type or task type lists it, or a workflow of this project type uses it. It reads that before the task types change: `OnTaskTypeUpdate` drops transitions to a status that left a list.
- `getClient().domainRequest` shows a platform status and returns `{ value: null }` on failure. `mergeStatuses` (`statusMergeApi.ts`) turns that into a refused result, `getStatusUsage` throws a `PlatformError`. Check `isOwnerOrMaintainer()` before the usage request, otherwise the pipeline shows a Forbidden banner.
- Rename: `Status.name` is updated in place when the id has no ':' (model builders name docs `tracker:status:Backlog`, `generateId` has none) and no other project type lists the status (`canRenameStatusInPlace`). `createdBy` does not work as a marker: the importer creates statuses as System. Otherwise `renameStatusByMerge` (`plugins/task-resources/src/statusRename.ts`): `createStatusAtomic` with `exclude` = the old status puts a new status right after the old one in the target task types (`placeStatusAfter`), then the server merge old -> new runs with `taskTypes` = those task types. Without `exclude` a case-only rename ("In Progress" -> "In progress") resolves to the status itself. The merge moves tasks (archived and foreign spaces included), rewrites the project type entries and `statusOrder`, and rewrites workflows before the old status leaves the lists, so no transition is lost. The delete of a status from one task type is the same merge with `taskTypes: [that type]`.
- A refused rename merge takes the placement back (and the new `Status` when it was created now) only when it wrote nothing: the usage request shows no tasks and no project defaults for the new status, no workflow uses it, and every target task type still lists the old one. Otherwise the placement stays: saving again finishes the merge, the writes are resumable.
- `Card` closes its dialog when `okAction` resolves and stays blocked when it rejects, so a dialog that keeps a failure on screen is a `Modal` (`AddExistingStatusPopup`). `createStatusesAtomic` throws `PlatformError` with `task.status.*` codes; `getStatusErrorText` (`plugins/task/src/utils.ts`) translates them for inline messages.
- Importer on a category conflict appends the category `defaultStatusName` to the name (`createStates`).
- `createStatusAtomic` (`plugins/task/src/utils.ts`): `ApplyOperations` with scope `task-status:<type>` and `match` ProjectType `{_id, modifiedOn}`. `ApplyTxMiddleware` evaluates `match`/`notMatch` only when `scope != null` and serializes applies of one scope inside one transactor process. A failed commit returns `{result: false}`. No `notMatch` on Status name: statuses are global, other project types have the same names. `modifiedOn` is not bumped by System txes.
- `ProjectStatus.taskType` is optional: an entry without it is a status of the project type in no task type. `calculateStatuses` rebuilds entries from task types and keeps one task-type-less entry per status that no task type has. `OnTaskTypeRemove` leaves the removed task type's `Status` docs and tasks alone; before it, `ProjectType.tasks` kept the dangling ref and the next recalculation dropped the entries silently.
- `getProjectTypeStates` returns the task-type-less entries (the settings screens use it); `getStates` and `getProjectTypeStates(..., true)` skip them: pickers, kanban drop zones, `StatesBar`, `Dashboard`, `StatesPopup` and the transfer targets of `deleteProjectTypeStatus` list only statuses some task type lists. Readers of `ProjectType.statuses` that bypass both helpers filter on `taskType` themselves (tracker `StatusSelector`, `TypeStatesPopup`, `StatusFilter`).
- `ProjectType.statusOrder` absent means the old merged order. The server merge rewrites it with `mapStatusOrder`: the target takes the place of the source, and a source that a task type outside the `taskTypes` scope still lists stays with the target right after it. `mergeProjectStatusEntries` drops a task-type-less entry of a status that has typed entries after the merge.
- Transfer mode of `checkStatusMerge`/`mergeStatuses` (`MergeStatusesParams.transfer`): category may differ, an existing source outside the project type is accepted; attribute must still match.
- Orphan status = `Status` of the status attribute of the project type's task types in no `ProjectType.statuses` and no `TaskType.statuses` of any project type (`getOrphanStatuses`). `Status.ofAttribute` is per base class, so it does not scope to a project type.
- The server rewrites `modifiedOn` of non-system txes, so `Client.updateFromRemote` copies the server `modifiedOn` from the echo of its own locally applied model tx onto the local doc; without it the `createStatusesAtomic` compare-and-set on `ProjectType.modifiedOn` fails after any local ProjectType update from this client. `ClientImpl.appliedModelTransactions` maps the tx id to the `modifiedOn` the local doc got from it, and the echo overwrites the doc only while it still has that value or an older one. A foreign tx on the same doc can reach the client before the echo (broadcasts of two sessions interleave): the doc keeps a newer foreign `modifiedOn` and takes the echo's over an older one. A copy on every echo would roll the doc back to the older value of an overtaken echo, and the compare-and-set would fail until the next change or a reload.
