# Status uniqueness in a project type

Область: [Tracker](../features/tracker.md)

- Before the change, a color-only edit in `CreateStatePopup` (`needUpdate` path) created a new `Status` with the same name and re-pointed the tasks of that task type: a source of duplicates besides the importer.
- `ProjectType.statuses` has one entry per (status, task type) from `calculateStatuses`, but a copy of the FIRST entry with that `_id` is used for all task types; `StatePresenter` also reads the first entry by `_id` only. Color/icon are effectively per project type.
- `createProjectType` / `createStates` on a same-name status in another category creates a new status (an import must not fail halfway); the UI blocks that case.
- Deleting a `Status` doc: `removeStatusFromType` (`plugins/task-resources/src/statusUsage.ts`) deletes it only when the id has no ':', no other project type or task type lists it and no `WorkflowTransition` has it as `to` (it does not check `from`, the arrays are not queryable in all adapters); with tasks or transitions the server merge runs with `transfer: true` and `splitReferenced` decides the removal. `DeleteStateConfirmationPopup` without `type` still only removes it from the task type.
- Rename: `Status.name` is updated in place when the id has no ':' (model builders name docs `tracker:status:Backlog`, `generateId` has none) and no other project type lists the status (`canRenameStatusInPlace`). `createdBy` does not work as a marker: the importer creates statuses as System. Otherwise create/reuse; a reuse that would move tasks from the browser (one update and notification per task) is blocked.
- Importer on a category conflict appends the category `defaultStatusName` to the name (`createStates`).
- `createStatusAtomic` (`plugins/task/src/utils.ts`): `ApplyOperations` with scope `task-status:<type>` and `match` ProjectType `{_id, modifiedOn}`. `ApplyTxMiddleware` evaluates `match`/`notMatch` only when `scope != null` and serializes applies of one scope inside one transactor process. A failed commit returns `{result: false}`. No `notMatch` on Status name: statuses are global, other project types have the same names. `modifiedOn` is not bumped by System txes.
- `ProjectStatus.taskType` is optional: an entry without it is a status of the project type in no task type. `calculateStatuses` rebuilds entries from task types and keeps one task-type-less entry per status that no task type has. `OnTaskTypeRemove` leaves the removed task type's `Status` docs and tasks alone; before it, `ProjectType.tasks` kept the dangling ref and the next recalculation dropped the entries silently.
- `ProjectType.statusOrder` absent means the old merged order. `mergeStatuses` rewrites it with the id map (`mapStatusIds`), and `mergeProjectStatusEntries` drops a task-type-less entry of a status that has typed entries after the merge.
- Transfer mode of `checkStatusMerge`/`mergeStatuses` (`MergeStatusesParams.transfer`): category may differ, an existing source outside the project type is accepted; attribute must still match.
- Orphan status = `Status` of the status attribute of the project type's task types in no `ProjectType.statuses` and no `TaskType.statuses` of any project type (`getOrphanStatuses`). `Status.ofAttribute` is per base class, so it does not scope to a project type.
- The server rewrites `modifiedOn` of non-system txes, so `Client.updateFromRemote` copies the server `modifiedOn` from the echo of its own locally applied model tx onto the local doc; without it the `createStatusesAtomic` compare-and-set on `ProjectType.modifiedOn` fails after any local ProjectType update from this client.
