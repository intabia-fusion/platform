# `generate-demo-data` tool command

`dev/tool/src/demoData.ts` + `generate-demo-data <workspace>` in `dev/tool/src/index.ts`. Imports a Unified Format dir (`--dir`, default `tests/demo-ws`) via `@hcengineering/importer`'s `HulyFormatImporter`, reusing `setupAccount`/planner helpers exported from `plannerData.ts`. Stand: `docs` in `dev/test-base/src/stands.ts` (`tests/prepare-pg.sh --docs`), which seeds two demo sets: `demo-ws` (Russian, accounts `demo1..demo4`) and `demo-ws-en` (English, accounts `demo-en1..demo-en4`, dir `tests/demo-ws-en`).

- All text/layout that `demoData.ts` fills in after the import (components, milestones, labels, due dates, chat channels+threads, personal todos, calendar events) lives in a sibling `<dir>.data.yaml` file (`tests/demo-ws.data.yaml` / `tests/demo-ws-en.data.yaml`), not in the importer's own folder: `huly.ts`'s `processImportFolder` treats every `*.yaml` directly inside the Unified Format dir as a space and only skips one without a `class` field with a logged error (non-fatal, but noisy) - keeping the data file as a *sibling* of the dir avoids that entirely instead of relying on the non-fatal skip.
- Tracker identifiers (`APP-1`, `MKT-4`, ...) are the same between the ru and en demo sets (same issue count/order/status/priority per project), so `issueComponents`/`issueMilestones`/`issueLabels`/`issueDueDates`/`workSlotIssues` in both data files use identical keys - only the component/milestone/tag/channel/event *text* differs. Components/milestones/tags are referenced by a stable `key` (e.g. `ios`, `release10`, `bug`), not by their display label, so the label can be translated freely.
- Chat messages reference their author as a 1-based index into `--accounts` (1=lead, 2=developer, 3=designer, 4=tester); a message's `replies` are posted as thread replies to that message, by the same indexing.

- `createRestTxOperations` (REST `TxOperations`) works fine for the importer, including `.apply()`: `ApplyOperations.commit()` just calls the wrapped client's generic `tx()`, which `RestTxClient.tx` implements like any other transport. No need for the WS-based `createClient` from `@hcengineering/server-client`.
- Unified Format `assignee` is matched by **full name** (`person.name` reversed, "Имя Фамилия"), but `comments[].author` is matched by **login** (`SocialIdentity` of type EMAIL) - i.e. the account name passed to `create-account`, not the display name.
- `FrontFileUploader`'s `frontUrl` is the same base `PLATFORM_URL` used for `loadServerConfig`/`getWorkspaceToken` - front is proxied at the stand's root (`http://localhost:8083`), there is no separate `FRONT_URL`.
- `Issue.assignee`/`.milestone` are `Ref<Person>`/`Ref<Milestone> | null`, not `Ref<Employee>` - caught by `tsc`, not obvious from the plugin's doc comments.
- `chunter` ships a ready `postMessage(client, channel, message)` helper (`plugins/chunter/src/ops.ts`, re-exported from the package). Thread replies have no such helper: `addCollection(chunter.class.ThreadMessage, channelId, parentMessageId, chunter.class.ChatMessage, 'replies', { message, objectId: channelId, objectClass: chunter.class.Channel })`.
- Labels: `createDoc(tags.class.TagElement, core.space.Workspace, { ..., category: tags.category.NoCategory })`, then `addCollection(tags.class.TagReference, issue.space, issue._id, issue._class, 'labels', { tag, title, color })`.
- `tracker.class.Component`/`Milestone` are created with `createDoc(class, projectId, {...})` - the project id doubles as their `space` (a `Project` is itself a `Space`).
- A whole-workspace `pnpm install --offline` can fail on unrelated pre-existing lockfile/cache drift (e.g. missing `v8-compile-cache` metadata) unconnected to the actual change. A scoped `pnpm install --filter @hcengineering/tool...` (online) is enough after adding a workspace dependency and does not touch unrelated importers' lockfile entries beyond harmless dead-snapshot pruning.
