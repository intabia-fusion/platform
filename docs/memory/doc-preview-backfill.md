# DocPreview: backfill и порядок миграций

Область: [Уведомления](../features/notifications.md), [Чат](../features/chat.md)

## Миграции

- SQL-миграции db-migrator выполняются при старте сервисов, раньше миграций модели (апгрейд воркспейса). Поэтому backfill ссылок `Chat.preview` и `DocNotifyContext.preview` нельзя сделать одним UPDATE в db-migrator: превью появляются только из миграции модели `doc-previews-v3:<класс>`. По той же причине колонки ссылок nullable: `NOT NULL` можно поставить только после апгрейда всех воркспейсов.
- `doc-previews-v3:<класс>` - состояние `tryMigrate` на каждый класс с превью (`hasPreview` по `getDescendants(core.class.Doc)`, точное `_class`): класс, получивший `ActivityDoc` или `ClassCollaborators` позже, добирается следующим апгрейдом. Документ, у которого превью уже есть, пропускается: второе нарушило бы уникальный индекс.
- Ссылки контекстов (`context-previews-v1`) - в миграциях notification, последним шагом: `migrate-notifications-to-embedded-v6` создаёт контексты без `preview`, а `activityServerOperation` в `models/all/src/migration.ts` идёт раньше notification. Шагу презентеры не нужны, только таблица превью.
- Апгрейдер (`server/workspace-service/src/service.ts`, `registerServerPlugins`) загружает ресурсы серверных плагинов: `getPreviewData` из server-activity зовёт те же презентеры, что триггеры. `PresenterControl` над `MigrationClient` - `presenterControl` (models/server-activity/src/migration.ts): `findAll` идёт в домен класса или в `client.model`, кеша нет. Презентеры могут ходить в базу (`ReminderTitlePresenter` - цель события, `TrainingRequestTitlePresenter` - тренинг, `getIssueId` - проект для задачи без `identifier`).
- `rawUpdate` postgres (путь `MigrationClient.update/bulk`) пишет в колонку значение после `applyUpdate`, а не операнд оператора, через `convertDoc` по схеме колонки: `$inc` - сумма, `$unset` nullable-колонки - NULL, `$unset` NOT NULL-колонки - заглушка, как при вставке (`0`, `false`, `''`, `[]`). Основной путь `txUpdateDoc` пишет `doc[key]`, и там `$unset` NOT NULL-колонки падает. Тесты - `storage-coverage.itest.ts`, «rawUpdate stores what an operator leaves in a column» и «rawUpdate unsets a nullable column to NULL…».
- Шаг миграции при брошенной ошибке `tryMigrate` не отмечает и на следующем апгрейде начинает заново, поэтому внутри шага ошибки не бросаются: плохой документ, строка или батч логируются и пропускаются (`written`, `createEach`/`updateEach` из `@hcengineering/model`: батч, упавший на одной строке, повторяется по строкам).
- В `MigrationDocumentQuery` `{ $exists: false }` по колонке работает как `IS NULL`.
- На пустой базе db-migrator файлы не выполняет, а помечает применёнными и ставит версию схемы (`isDatabaseEmpty` -> `markAllAsApplied`): таблицы создаёт адаптер по `schemas.ts`. Таблица, созданная образом без колонки `preview` (например, сборкой develop после очистки базы), её уже не получит: транзактор пишет `table is missing declared columns`, значения уходят в `data` jsonb. Простой `ADD COLUMN` такие значения скроет (пустая колонка перекрывает `data`, а фильтры и join идут по колонке) - их надо перенести: `UPDATE ... SET preview = data->>'preview', data = data - 'preview'`.
- Старый бэкап (sanity-ws, 2024) приносит в `model_tx` 2011 системных txes старой модели. Их удаляет core `clean-old-model`, но иерархию миграций `upgradeModel` собирает один раз до него, из системной модели и txes базы. Старые txes шли после текущих и заменяли классы целиком (повторный `TxCreateDoc` классификатора перезаписывает его): у `Channel`, `Person`, `Milestone` пропадали `TitlePresenter`/`IconPresenter`/`titleKey`. Backfill писал превью с пустыми заголовками и без иконок, без ошибок; в навигаторе каналы назывались «Channel». Совсем убрать старую модель нельзя: `migrateAccounts`/`migrateCollaborators` читают миксин `notification:mixin:Collaborators`, который есть только в ней. Поэтому, пока `clean-old-model` не отмечен, `oldModelFirst` (server/tool/src/index.ts) применяет старые системные txes первыми, затем текущую модель, затем остальные txes базы.
- Тест, создающий документ через REST сразу после `loginByToken`, обгоняет первый вход: у владельца ещё нет `PersonSpace`. `OnCollaboratorAdded` (как и в develop) пропускает аккаунт без личного пространства, и чата документа у него не будет никогда. Перед созданием надо дождаться чата `general` в навигаторе: он появляется вместе с пространством.
- `context-display-copies-v1` переносит lite-копию сообщения треда из старого `object` контекста в `message` (та же форма `toNotificationMessage`) и снимает копии отображения (`objectTitle/Identifier/Label/Icon`, `parentObject*`, около 6% данных страницы инбокса). Без шага старые треды в инбоксе остались бы без текста. Шаг идёт двумя проходами `traverse` по `$exists` (`objectTitle`, затем `object`): `$or` в запросах миграций postgres не используется, а курсор `traverse` - снимок, правка строк его не сдвигает. Колонки `parentObjectId/parentObjectClass` и индекс по ним (db-migrator 0001/0010) код не читает и не пишет; они остаются до следующего релиза: прежняя версия пишет в них, и откат на неё после удаления сломал бы запись контекстов.
- Контексты на `ProjectToDo` создавались, потому что `ToDoReassigned` срабатывает на `TxUpdateDoc` без `attachedTo`. `getNotifiedDoc` берёт родителя из `attachedTo` документа, такие контексты больше не появляются; существующие удаляет `remove-todo-contexts-v1` (models/time).

## Какие классы получают превью

- Превью уникально по `(objectDomain, objectId)`: id документа повторяется между доменами, а класс может смениться (`OnDocPreviewMoved`). Везде, где превью ищут по документу (триггеры, сервис, ссылки чатов и контекстов, `createChats`), ключ - домен и id; по классу не ищут.
- Классы без `ActivityDoc` попадают в `hasPreview` только через коллабораторов: чату это не нужно (чаты создаются только для `ActivityDoc`), а инбоксу нужно - уведомления, а с ними контексты, есть у QMS-документов, `request.Request`, `setting.Integration`. События, рабочие слоты и to-do с наследниками (`ProjectToDo`, `ProcessToDo`, `ApproveRequest`) исключены отметкой `NoPreview` (models/server-calendar, models/server-time). `ActivityDoc` сильнее отметки, иначе `Review` (наследник `Event`) потерял бы превью и чат. Превью, созданные до исключения класса, миграция не удаляет: при исключении класса с существующими превью нужен отдельный шаг.
- `titleKey` у большинства классов задан на предке (`Card`, `Space`, `Room`, `drive.Resource`): серверный `getDocTitle` берёт его по цепочке предков, как клиентский. `DocumentCategory` и `contact.Channel` получили `titleKey` в модели ради превью.
- Пропсы `icon.props` серверных `IconPresenter` совпадают с пропсами клиентских `ObjectIcon`-компонентов (`ChannelIcon` asset/emoji, `DirectIcon` members, `PersonIcon` _id, `IssueStatusPresenter` space/kind/status, `DocumentIcon`/`CardIcon`/контактный `ChannelIcon` - `value` от `FieldsIconPresenter`), поэтому компонент класса рисуется из превью как есть.
- `data jsonb` возвращает ключи объектов в своём порядке (короче - раньше): `{members, type}` приходит как `{type, members}`. Поэтому `previewUpdate` сравнивает превью с новыми данными без учёта порядка ключей; `JSON.stringify` считал бы `props`/`icon` изменёнными при каждом обновлении.

## Триггеры

- Превью создают только синхронные `OnDocCreated`, `OnDocPreviewMoved` (смена класса) и backfill. Асинхронные триггеры (`OnDocUpdated`, `OnCollaboratorAdded`) превью не создают: два параллельных запроса на документ без превью вставили бы его дважды, а нарушение уникального индекса в `processDerivedTxes` роняет все асинхронные производные транзакции запроса (чаты коллабораторов, ссылки). Документ, записанный миграцией в обход триггеров после backfill своего класса, остаётся без превью: такая миграция делает превью сама (`newPreview`).
- Пространство превью переносит синхронный `OnDocPreviewMoved`: асинхронный перенос более старого запроса может прийти последним и оставить превью приватного документа в публичном пространстве. Синхронные триггеры разных запросов тоже не упорядочены, остаётся окно в миллисекунды между чтением документа и записью превью; 10 одновременных переносов двумя клиентами расхождений не дали. Асинхронный `moveContexts` читает пространство из документа; его гонка оставляет только устаревший `objectSpace` и снимок контекста, превью не открывает.

## Доступ

- `SpaceSecurity.filterLookup` вырезает из join превью архивного пространства (у превью пространства `space` - оно само) и документов в нём, если запрос не `showArchived`: инбокс запрашивает с `showArchived: true`, навигатор - без него (чаты задач архивного проекта в навигаторе не показываются). Вырезание идёт после `limit`, и вырезанные строки занимают места окна: свежие чаты архивного проекта могут занять всё окно секции из 5 и скрыть её вместе с «показать ещё». Поэтому секция добирает окно повторным запросом с `limit + extra` (`extra` удваивается: длинная серия вырезанных строк - несколько запросов, а не по одному на окно) и показывает не больше `limit`. В SQL фильтр по доступным пространствам не перенесён: у гостей исключения.
- `addSecurity` (postgres) пропускает документы публичного пространства неучастнику, только если запрос называет `space`, `_id` или `attachedTo`: запрос превью по `{ objectId, objectDomain }` без `space` вернёт пусто для публичного проекта, где пользователь не состоит.
- `ReadOnlyGuest` - один общий аккаунт `readOnlyGuestAccountUuid`, а не роль многих: триггер узнаёт его по uuid, роли других пользователей ему недоступны.
- Снимок превью в контексте (`previewSnapshot`) пишется только при потере доступа, а не при каждом уведомлении: живое превью остаётся у всех, кто его читает, а переименование не размножается по контекстам. Ушедший видит заголовок на момент потери доступа (новые названия ему не положены); его контексты и уведомления остаются. Выдержки сообщений контекст и так хранит, поэтому заголовок в снимке ничего нового не открывает. `objectSpace` контекстов переносит `OnDocSpaceChanged`: по нему триггер пространства находит контексты документов. Миграция `context-preview-snapshots-v1` проверяет доступ по `space` превью, а не по `objectSpace` контекста: у контекстов, созданных до триггера, `objectSpace` мог устареть, и миграция его исправляет (кроме контекста чата самого пространства - у него `objectSpace` остаётся тем, где создано пространство).

## Клиент

- Хелперы отображения превью (`getPreviewTitle`, `previewTitle`, `getPreviewIcon`, `PreviewIcon.svelte`) лежат в view-resources: инбокс и навигатор рисуют одно и то же, chunter-resources зависит от notification-resources (обратный импорт дал бы цикл), а имена участников DM view-resources получает ресурсом `contact.function.GetParticipantsName` (contact-resources сам зависит от view-resources).
- Кэш строк навигатора (`ChatNavSection`, `built`) сравнивает превью и чат по ссылке: LiveQuery правит `$lookup` на месте только в своей копии, а подписчику отдаёт клоны (`ResultArray.getResult`), и изменённый документ получает новый клон вместе с `$lookup` (`updateDoc`); неизменённые сохраняют объект. `doRefresh` и новый запрос отдают всё новое - разовая пересборка.
- Навигатор держит только превью, и клик по чату документ не приносит. Канал или DM открывается по `_id/_class` сразу, `object` в цепочке до `ChannelInput` необязателен: ленте сообщений документ не нужен. `ChatMessageInput` получает `target: ChatTarget` (id, класс и пространство сообщения) вместо документа и отправляет без него; документ нельзя передать как `ChatTarget` напрямую - у пространства его `space` служебный, поэтому `getChatTarget`. `DocPreview.space` уже пространство сообщения. Тред передаёт ещё `parentMessage` ради `objectId/objectClass` ответа. `ChatMessagePresenter` без подходящего `doc` грузит документ чата только в `inline` (ссылка на документ), иначе был бы запрос на каждое сообщение; `ForwardedMessagePresenter` получает `doc` как кеш, поле правки собирает `target` из `attachedTo/attachedToClass/space` сообщения.
- Ссылка на канал или DM декодируется с классом `ChunterSpace`, а расширение ввода зарегистрировано на `Channel`/`DirectMessage`: пока `Chat.svelte` не заменит класс на класс пришедшего документа, ввод не находит расширения и не рисуется. Шапка тоже: без документа и без превью клика (открытие по адресу) она пустая - без заголовка, иконки, метки и боковой панели: `getChannelName` по `ChunterSpace` дошёл бы до `getDocLabel`, а у класса нет `label`, и `translate(undefined)` падает на `split`, а иконка и боковая панель канала мелькнули бы у директа. Поздняя расшифровка прежней ссылки (`parseLinkId`, задача по идентификатору) отбрасывается, если адрес уже сменился.
- Документ другого класса открывается в чате своей панелью (`ObjectPanel`, иначе `EditDoc`, `embedded`) по `_id/_class`, адрес `<id>|<class>` остаётся в чате, документ для клика не нужен. Переход к его сообщению из Saved, Threads и поиска (`openSearchResult`) ведёт туда же.
