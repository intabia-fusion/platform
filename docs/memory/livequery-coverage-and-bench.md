# LiveQuery: покрытие, бенчмарки и две найденные дыры

Сессия 21.09.2026. `foundations/core/packages/query` был 69.5% statements при 187 тестах,
стал 95.81% (без `catch`-блоков) при 289. Ниже только неочевидное.

## Две реальные ошибки, найденные покрытием

**Повторно доставленная `$inc`-tx инкрементила дважды.** `handleDocUpdate` применяет
equal-timestamp `$inc`-only tx локально, а `__updateDoc` при этом *чистит* `loadedModifiedOn` и
двигает док на `tx.modifiedOn`. Та же tx пришла ещё раз (реплей после реконнекта, двойной
notify) - снова подходит под `incOnlyAtSameTime`. Первый заход помечал применённые tx только в
equal-timestamp ветке - промах мимо реального пути счётчика комментариев, где issue создан
раньше комментария и первая доставка идёт веткой `updatedDoc.modifiedOn < tx.modifiedOn`.
Помечать надо на **каждом** применении `$inc`-only tx. Тесты: `inc-match.test.ts`, два
"ignores a re-delivered $inc tx ...".

**Запаркованный запрос утекал на `BulkUpdate` и `SecurityChange`.** У `IndexingUpdate` есть
`else { this.removeQueue(q) }`, у двух других нет. `removeFromQueue` убирает запрос из LRU
(`this.queue`) и из `refs`, но оставляет в `this.queries` - дальше он бессмертен: из очереди
выпал, значит `remove()` не вытеснит, а второй безусловный проход обработчика ещё и рефрешит
его на сервере. Проверка: заполнить LRU (CACHE_SIZE 125) 140 запросами, после этого повторная
подписка обязана сходить на сервер. Тесты в `workspace-refresh.test.ts`.

## Ветка, которая выглядит багом, но ею не является

`if (!this.removeFromQueue(q))` в `checkUpdateEvents`/`changePrivateHandler` недостижима: в
`this.queue` кладут только запросы с пустым `callbacks`, а `getQuery` при повторной подписке
снимает запись из очереди **до** `pushCallback`. Оставлена как есть - по смыслу верна.

## Ловушки при написании тестов на этот пакет

- `Date.now()` имеет миллисекундное разрешение. `createDoc` + сразу `updateDoc`/`createMixin`
  попадают в ту же миллисекунду, код уходит в `getCurrentDoc` вместо локального применения.
  Нужна пауза 2-5 мс, иначе тест проверяет не ту ветку.
- Колбэки коалесцируются (`queriesToUpdate`): считать вызовы колбэка бесполезно, критерий
  завершения - появление последней записи в данных.
- Мок в `connection.ts` не поддерживает `$search` (любой непустой `$search` даёт пустой
  результат, `matchQuery` считает его обычным полем) и не фильтрует по полям миксина.
- `ts-jest` проверяет типы слабее `tsc`: сьют зелёный, а `pnpm build:lint --to @hcengineering/query`
  падает. Проверять обоими.

## Бенчмарки

`src/__tests__/livequery.bench.ts`, запуск `pnpm bench` в пакете. Обычный прогон не берёт:
`testMatch` ловит только `*.test.ts`. Хранилище in-memory, меряется сам LiveQuery.

Порядки на ноутбуке (22.09.2026): первая подписка ~8 мкс/док, findOne из кэша `Refs` ~6 мкс против
~63 мкс мимо кэша. Разброс между прогонами до 20% - порог по времени ставить нечему.

## Где были тормоза на обновлениях

Профиль снят через `inspector.Session` прямо внутри jest-теста (временный файл, удалён):
отсекает разогрев jest, меряет только нужный участок. Анализ - агрегация `hitCount`
по `callFrame` из `.cpuprofile`.

Диагноз: **65% времени обработки tx уходило в `Refs.updateDocuments`**. `LiveQuery.callback()`
на каждый tx перерегистрировал в `Refs` **весь результат запроса целиком**, хотя изменился один
документ. Цена = подписчики x размер результата x число tx, плюс три аллокации на документ
(конкатенация classKey, `filter` нового массива `queries`, spread нового `DocumentRef`).
Отсюда суперлинейный fan-out.

Три правки (22.09.2026):
- `Query.refsRegistered` - полный проход только когда результат заменён целиком (первая загрузка,
  `doRefresh`, `cleanQuery`, снятие регистрации при парковке). Документы, входящие в результат по
  одному, регистрируются на месте: добавлены два `updateDocuments(q, [doc])` рядом с `result.push`.
- `DocumentRef.queries`: массив -> `Set`. При N подписчиках на один класс проверка членства была
  линейной по N.
- Тело цикла в `updateDocuments` мутирует существующую запись вместо пересборки.

Кэш `classKey` на один класс там же пробовали и убрали: A/B в три пары прогонов не дал разницы,
разброс внутри одной конфигурации оказался больше, чем между ними. Бенчить только на свободной
машине - под параллельным прогоном Playwright те же числа плавали вдвое.

Результат (мкс на tx, `pnpm bench`):

| случай | было | стало |
|---|---|---|
| update tx, 1 подписчик | 84 | 24-30 |
| fan-out 10 подписчиков | 350 | 209-220 |
| fan-out 50 подписчиков | 2301 | 434-465 |
| колбэк на результате в 1000 док | 388 | 48-54 |
| findOne из кэша `Refs` | 6.1 | 6.1-6.6 |

Профиль "50 подписчиков, 300 tx": 897 -> 260 мс; "1 подписчик, результат 1000 док,
200 tx": 143 -> 5 мс. Fan-out стал сублинейным.

Осталось наверху профиля: `clone` (~20%, клон результата на каждый колбэк) и `predicate.js`
(~18%) - `matchQuery` пересобирает предикаты на каждое сопоставление, `$like` компилирует regexp
заново. Оба в `packages/core`, не в query.
## Инварианты регистрации в `Refs`

Весь результат регистрируется в `Refs` ровно один раз (`q.refsRegistered`), поэтому каждый путь,
который трогает результат по одному документу, обязан держать `Refs` в порядке сам. Второго
прохода, который бы это подчистил, нет.

- **Регистрировать объект из результата, а не аргумент.** `ResultArray.push` и `updateDoc`
  клонируют аргумент и возвращают сохранённый объект - в `Refs` идёт он. Иначе кэш указывает на
  копию, которую никто не обновляет, а правки на месте (`updateDoc(doc, false)` в
  lookup/association-путях) уходят мимо: `findFromDocs` отдаёт протухший `$lookup`.
- **`pop()` обязан снять регистрацию.** Док, вытолкнутый из окна `limit` (`handleDocAdd`,
  `updatedDocCallback`), в `q.result.getDocs()` больше не попадает, а clean-проход ходит только по
  нему - без явной чистки запись живёт в `Refs` вечно.
- **Членство не зависит от ревизии.** `Refs.updateDocuments` добавляет `q.id` в set всегда;
  `existing.lastUsed > d.modifiedOn` влияет только на замену `doc`/`lastUsed`. Запрос, держащий
  более старую копию, всё равно держит документ - иначе чужой clean удалит его из-под запроса.

Тесты: `__tests__/refs-registration.test.ts` (white-box по приватному `refs.documentRefs`).
