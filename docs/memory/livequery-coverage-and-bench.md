`foundations/core/packages/query`.

## Инварианты, не очевидные из кода

- `$inc`-only tx помечается применённой (`handleDocUpdate`) на **каждом** применении, а не только в equal-timestamp ветке - иначе повторно доставленная tx (реплей после реконнекта, двойной notify) применяется дважды: счётчик комментариев на issue, созданном раньше первого комментария, идёт веткой `updatedDoc.modifiedOn < tx.modifiedOn`, а не equal-timestamp. Тест: `__tests__/inc-match.test.ts`.
- Обработчики `IndexingUpdate`/`BulkUpdate`/`SecurityChange` (`checkUpdateEvents`, `changePrivateHandler`) обязаны звать `removeQueue(q)` для запроса, не найденного в LRU (`this.queue`) через `removeFromQueue`: `removeFromQueue` чистит `this.queue` и `refs`, но не трогает `this.queries` - без `removeQueue` запись остаётся в `this.queries` навсегда (в LRU не попадёт, `remove()` её не вытеснит). Тест: `__tests__/workspace-refresh.test.ts`.
- `if (!this.removeFromQueue(q))` в тех же обработчиках недостижима в штатном потоке: `this.queue` содержит только запросы с пустым `callbacks`, а `getQuery` снимает запись из очереди до `pushCallback`.
- Весь результат регистрируется в `Refs` ровно один раз за жизнь запроса (`q.refsRegistered`, сбрасывается в `doRefresh`/`cleanQuery`/при первой загрузке) - второго прохода, который бы досинхронизировал `Refs`, нет. Поэтому:
  - каждый путь, добавляющий документ в результат поштучно, обязан сам вызвать `refs.updateDocuments(q, [doc])`;
  - регистрировать нужно объект из результата (`ResultArray.push`/`updateDoc` клонируют аргумент и возвращают сохранённый объект), а не аргумент - иначе `Refs` держит копию, которую никто не обновляет;
  - `pop()` (вытеснение за `limit`) обязан снять регистрацию явно - документ, выпавший из `q.result.getDocs()`, для clean-прохода недостижим;
  - замена результата целиком (`doRefresh`, `cleanQuery`) обязана сначала снять старый результат clean-проходом: колбэк регистрирует только новый, и документ, которого в новом нет, остаётся в `Refs` и отдаётся `findOne` (FUSIO-1632). `cleanQuery` чистит сам - `doRefresh` после него видит пустой результат. Тест: `__tests__/findone-removed.test.ts`;
  - `Refs.updateDocuments` кладёт `q.id` в set безусловно, ревизия (`lastUsed`/`modifiedOn`) влияет только на замену `doc`/`lastUsed` - иначе запрос со старой копией документа терял бы его при чужом clean.
- Проекция и lookup (`src/projection.ts`): `_class`, `space`, `modifiedOn` LiveQuery дописывает только к включающей проекции базового документа; одни `$lookup.`-ключи оставляют его целым; из исключения эти три ключа вычёркиваются, и если ключей не осталось, `projection` из опций убирается совсем (пустой объект адаптер читает как включение одних `_id`/`_class`, а ключ со значением `undefined` ломает сравнение опций по `deepEqual`); пустая проекция `{}` становится включением этих трёх полей. Серверный `LiveQueryMiddleware` (`queryFind` триггеров) крутит тот же пакет. Присоединённый документ запрашивается с проекцией своего пути (`lookupProjection`), вложенный - со своей; транзакция по нему всегда патчит результат, колбэк идёт только на спроецированное поле (`lookupFields` + `txTouchesProjected`, миксин-написание `<mixin>.<attr>` сравнивается по голому имени с обеих сторон), без проекции по пути - на любое; смена состава обратного lookup будит всегда.
- `DocumentRef.queries` - `Set`, не массив (линейная проверка членства при N подписчиках на класс была узким местом). Тест на инварианты `Refs`: `__tests__/refs-registration.test.ts` (white-box, приватный `refs.documentRefs`).

## Ловушки при написании тестов на этот пакет

- `Date.now()` - миллисекундное разрешение: `createDoc` + сразу `updateDoc`/`createMixin` попадают в ту же миллисекунду и уходят в ветку `getCurrentDoc` вместо локального применения - нужна пауза 2-5 мс, чтобы тест проверял нужную ветку.
- Колбэки коалесцируются (`queriesToUpdate`): считать число вызовов колбэка бесполезно, критерий завершения - появление последней записи в данных.
- `core.class.Space` в `minmodel.ts` лежит в `DOMAIN_MODEL`: `LiveQuery.findAll/findOne` по нему уходят в клиент напрямую, минуя дописывание `_class/space/modifiedOn` к проекции и кеш `Refs`. Обратный lookup (`_id: { kids: ... }`) у добавленного документа запрашивается, только если у него есть счётчик коллекции с этим именем (`kids > 0`).
- Тестовый мок в `connection.ts` не поддерживает `$search` (непустой `$search` даёт пустой результат) и не фильтрует по полям миксина.
- `ts-jest` проверяет типы слабее `tsc`: сьют может быть зелёным, когда `pnpm build:lint --to @hcengineering/query` падает - проверять обоими.

## Бенчмарки

`src/__tests__/livequery.bench.ts`, запуск `pnpm bench` в пакете (обычный `pnpm test` его не берёт - `testMatch` в `jest.config.js` матчит только `*.test.ts`). Хранилище in-memory, меряется сам LiveQuery. Профилировать точечно (без разогрева jest) можно через `inspector.Session` внутри самого теста - отсекает старт jest и меряет только нужный участок.

Разброс между прогонами бенча - до 20%, а под параллельным прогоном Playwright числа плавают вдвое - бенчить только на свободной машине, порог по времени ставить нечему.

На последнем профилировании (22.09.2026) поверх инвариантов `Refs` выше в топе профиля оставались `clone` (~20%, копия результата на каждый колбэк) и `predicate.js` (~18%, `matchQuery` пересобирает предикаты на каждое сопоставление, `$like` компилирует regexp заново) - оба в `packages/core`, не в `query`.

`findOne` из `Refs` по `_id` - точечный lookup в `Map`, ~3 мкс независимо от размера. По любому другому полю (`limit === 1` ветка `Refs.findFromDocs`) - полный проход: `Array.from` всех документов класса + `matchQuery` фильтрует весь массив, без выхода на первом совпадении. Замер 26.10.2026: 200 документов в `Refs` - ~50 мкс, 2000 - ~450 мкс на вызов. В `livequery.bench.ts` этот путь не покрыт.
- Поле-массив ссылок (`participants: [p1, p2]`) `getLookupValue` в LiveQuery и в `MemDb` разворачивает через `findAll({ _id: { $in } })` в массив документов, как сервер, вложенный lookup - по каждому элементу. Тесты lookup-проекции: `lookup-projection.test.ts` (хелперы, подгрузка с проекцией, колбэки), `lookup-projection-live.test.ts` (пересортировка по `$lookup`-полю, смена ссылки, `$push` и массив ссылок, члены обратного lookup, миксины, `findAll`/`findOne`), `core/src/__tests__/memdb.test.ts` (массив ссылок в `MemDb`, класс `TestHolder`).
- Транзакция той же миллисекунды, что и документ (`modifiedOn` равны), идёт не через патч `__updateDoc`, а через `getCurrentDoc` и полную перечитку: в тесте, который проверяет путь патча (подгрузка ссылки с проекцией), перед обновлением нужен `settle()`.
- Тесты пакета query берут `@hcengineering/core` из собранного `lib` (в стеках видны `src`-пути только из-за source map): правка в core без `pnpm build --to @hcengineering/core` в тестах query не видна.
