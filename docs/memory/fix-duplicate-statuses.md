# Merge of duplicate statuses (button in the project type Statuses section)

Область: [Tracker](../features/tracker.md)

Client: `mergeStatuses(params)` (`plugins/task-resources/src/statusMergeApi.ts`) sends `domainRequest(statusMergeDomain, params)`, `getStatusUsage` in the same file sends `statusUsageDomain`; contract types in `plugins/task/src/statusMerge.ts`. Server: `TaskMiddleware.domainRequest` (`server-plugins/task/src/middleware.ts`), logic in `statusMergeOps.ts`.

- Role Maintainer or higher; only same-category statuses of one project type. `ok: false` means nothing was written.
- The merge writes as the system account, below the middlewares that watch `tx`, so `TaskMiddleware` refuses the caller itself before it runs: `SessionData.readOnly` (token `readonly`, set in `ClientSession.includeSessionContext`; WorkspaceReadOnly), an API key without write access, with named operations only or limited to spaces, and `SessionData.seatReadOnly` (set by `SeatLimitsMiddleware.domainRequest`) - both Forbidden. `domainRequestRaw` does not reject read-only sessions: other domain requests are reads.
- Params are checked at entry (`checkMergeParams`, BadRequest): an object in place of an id (`{ $ne: '' }`) would reach the queries as an operator. `taskTypes` must be a non-empty list; ids outside `ProjectType.tasks` give a refused result.
- Everything is checked first against the planned state with the real workflow functions (`hasSelfTransition`, `getTransitionConflict`, the task transition rule of `WorkflowMiddleware.validateTaskUpdate`); one conflict stops the merge. Transition validators are not pre-checked.
- Write order, so that a failed run is finished by running the merge again: 1) the target joins every task type list and project type entry that has a source, sources stay; 2) workflows: initialStatuses, transitions to/from, subtask and parent rules; 3) tasks; 4) project default; 5) history; 6) sources leave task types, project type entries and `statusOrder`; 7) removal of unreferenced sources, saved filters. Until step 6 the sources are still listed, so a re-run finds them. A failure after step 6 leaves an orphan source: merge it again with `transfer: true`.
- Neither `WorkflowMiddleware` nor `TaskMiddleware` checks that a task status is in the task type list, only the transition rule.
- `mergeProjectStatusEntries` gives every entry of the target the color, icon and description of the target's own entry: `StatePresenter` and `calculateStatuses` take the first entry of a status, so a source entry of another task type would recolor the target.
- Subtask and parent status rules (`WorkflowTransition.validators[].props.statuses`, per task type) are rewritten in every workflow of the project type. Until step 6 a rule lists the target next to the sources: tasks move in arbitrary order, and a parent or subtask that has not moved yet would fail the rule. A source named by a rule of any workflow is kept.
- Every flush (100 txes) is broadcast on its own, also by a merge that fails: `QueueMiddleware` publishes `broadcast.txes` in `handleBroadcast`, and over 10000 txes a broadcast collapses into a bulk update without the model txes. The session data is shared by all flushes, so its broadcast buffers are reset after each one and `asyncRequests` run once.
- `taskTypes` (scope): only those task types take the target. Rules are rewritten for their keys in all workflows, `statusOrder` keeps a source that a task type outside the scope still lists and inserts the target after it, the project default moves only when no task type lists the source after the merge, history is that of the moved tasks (`attachedTo`), removal is unchanged.
- History is read as status messages only (`attributeUpdates.attrKey = 'status'`; Postgres reads the dotted path from `data`), by pages of 1000 by `_id`; tasks are read with `status: { $in: sources }`.
- `statusUsageDomain` (`StatusUsageParams`, `StatusUsageResult`): Maintainer, allowed in read-only sessions. Queries run as the system account with `limit: 1, total: true, showArchived: true`: tasks of the status in the workspace, per task type of the project type, projects with it as the default.
- Writes carry `meta.silent`: the notification service skips such txes and messages, triggers and the activity service copy it onto what they generate. It does not keep activity quiet: a non-derived task update still adds a "status changed" message attributed to the last modifier. So task and project updates are derived txes (`space` is `DerivedTx`), which the activity and webhook services skip. Triggers match by class, `WorkflowMiddleware` and the broadcast look at the operations only. `TxMiddleware` does not store derived txes in the tx log; the model txes of the same merge still advance `lastTx`.
- Triggers stay on: `OnStateUpdate` re-emits `isDone` (bumps task `modifiedOn`), the workflow `PostFunctionsTrigger` runs post functions of a matching transition, `OnTaskTypeUpdate`/`OnStatusDelete` prune transitions to statuses that left the list (the order rewrites transitions first).
- TaskType and ProjectType keep a fresh `modifiedOn` on purpose: concurrent status creation compares it.
- A model-defined source (id contains ':'), or one that a task type or project type of another project type (or a task type outside the scope), a transition, a rule or a task still refers to after the merge, is kept (`kept` in the result).
- Pipeline `findAll` (`LookupMiddleware.cleanQuery`) drops scalar query fields from the returned docs: `findAll(X, { _id })` gives a doc without `_id`, and a tx built from it fails `NormalizeTxMiddleware` with BadRequest. The request restores the fields, and tests run every tx through the real `NormalizeTxMiddleware`.
- Model-defined statuses (ids with colons) are never removed; imported ones created by System are.
- SQL adapter ignores operators on nested arrays: DocUpdateMessage ids are checked in memory.
- Import creates the duplicates: `createProjectTypeWithTaskTypes` (`packages/importer/src/importer/importer.ts`) passes `factory` statuses to `createProjectType`; `createState` without `_id` always `createDoc`s.
- The task moves of a merge are derived txes, absent from the tx log, and the merge keeps the task's `modifiedOn`. The State History block of the issue card (`IssueStatusActivity.svelte`, `calcStatusDurations` in `statusHistory.ts`) therefore builds segments from the tx log and takes the current segment from `issue.status`: when it differs from the last status of the log, the log segment is closed at `max(last status tx, issue.modifiedOn)` and a segment of `issue.status` is opened. The switch time is an estimate. Segments of a status removed by the merge are skipped.
