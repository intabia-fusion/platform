# Onboarding widget + cards

- `OnboardingPreference.progress` - first-time timestamps by stable key (`opened`, `hintsOff`, `<cardId>:done`, `<cardId>:<actionLabel>`), analytics only: `preference` is a shared Postgres table with a `workspaceId` column (`docs/architecture.md`), the only place that can answer "how many people did what" across workspaces. Written by read-merge-write in `markOnboardingProgress` (`plugins/view-resources/src/onboarding.ts`), never overwrites. Auto-marking must not read it: "Start over" keeps `progress`, so a `<id>:done` key says nothing about the current run.
- Auto-marking is blocked only by `OnboardingPreference.dismissed` (ids unticked by the user after completion); "Start over" clears it and resets `startedAt`.
- `doneWhen` queries add `createdOn >= startedAt`; without it a new member of an existing workspace gets steps ticked by old data. Preferences created before `startedAt` existed get it on the first widget open, so their first run counts from then.
- AI Julia and Invite cards stay manual: bot account is resolved asynchronously in `ai-bot-resources` (`getBotAccount`), which `workbench-resources` cannot depend on; invites live in the account DB. Calls uses `love.class.MeetingMinutes` with `byMember`; a meeting created before `startedAt` and joined after is not counted.
- Card action labels reuse the i18n key of the real button (`chunter.string.NewChannel`, `tracker.string.NewIssue`, ...). `models/drive` has no dependency on `uploader`, so its upload card uses the literal `'uploader:string:UploadFiles'`; same for `'setting:string:InviteWorkspace'` in `models/workbench`. The spotlight selector is the button's `data-id`, which `HeaderButton` derives from the action id (`tracker-string-NewIssue`); the main button becomes `ResumeDraft` when a draft exists, so the tracker selector lists both.
- `models/document` and `models/drive` import `OnboardingCard` from `@hcengineering/model-workbench` (re-exported there) instead of `@hcengineering/workbench`: a direct dependency would need a `package.json` + lockfile change.
- `OnboardingCard` and the widget doc are `DOMAIN_MODEL`: on a dev stand they appear only after the server redeploys the model. With an old model the settings page shows "0 of 0" and "Open panel" is a silent no-op (`if (widget === undefined) return`).
- Calendar has no top-level `Application`; its Meetings card is attached to the Planner app (`time.app.Me`).
- Old card ids stay in users' `completed`: `tracker:ids:OnboardingProjectsCard` (was "issue created", now "project created") and `drive:ids:OnboardingFilesCard` keep their id, `OnboardingNavigationCard` is gone and its stale id is ignored by the counter (it counts only visible ids).
