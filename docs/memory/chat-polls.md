# Чат: опросы (апплеты)

Область: [Чат](../features/chat.md).

## Путь голоса

- `services/activity/src/worker.ts` отбрасывает tx из `DOMAIN_TRANSIENT`, транзиентный `VotePollAction` проходит только явным исключением. Без исключения голоса молча перестанут доходить.
- Сервис activity применяет результат через REST `TxApplyIf`. Эхо этой tx уходит в Kafka только после ответа REST (`handleBroadcast` после `sendResponse` в `foundations/server/packages/server/src/client.ts`), так что следующий голос из партиции может опередить эхо предыдущего. Поэтому `VotePollHandler` читает опрос и ответ из БД, а не из кэша, который обновляется по эху. Голоса одного воркспейса обрабатываются строго по очереди: одна партиция, `eachMessage`.
- `TxApplyIf` - не одна транзакция БД: `PostgresAdapter.tx` пишет домены по очереди, каждый запрос коммитится сам, без отката. Если запись оборвалась после `PollAnswer`, повтор с тем же телом падает на первичном ключе ответа и до опроса не доходит. Поэтому голос с уже записанным ответом и отмена без ответа при передоставке из Kafka пересчитывают итоги по `PollAnswer` (`syncWithAnswers`). Считать по `{ options: id }` в запросе нельзя: `escape()` адаптера выкидывает из значения символы вне `[A-Za-z0-9_.:\-$ ]` и кириллицы.
- Оборванный голос узнаётся по счёту, не по времени: у анонимного опроса число `PollAnswer` не сходится с `totalVotes`, у неанонимной викторины голосующего нет в `userVotes` (`isVoteMissing`). Время ответа и опроса ставят разные часы (сервис и transactor). Пересчёт читает все ответы опроса, поэтому запускается только для оборванного голоса, а не на каждый повторный.
- Если обработчик в `services/activity` бросает ошибку, Kafka повторяет сообщение бесконечно и держит всю партицию. Форму голоса и опроса проверяет только middleware (`BadRequest`), обработчик доверяет данным: мимо middleware опросы пишет лишь сам сервис. Импорт опросов системным аккаунтом эти проверки обойдёт, его данные надо проверять при импорте.
- id варианта ключует `votes`: имя из `Object.prototype` (`constructor`, `__proto__`) ломает подсчёт (`votes[id] ?? 0` вернёт функцию). Middleware пускает только `[A-Za-z0-9_-]{1,64}` не из прототипа.
- Апдейт опроса от сервиса должен быть идемпотентным. Live query применяет апдейт к документам из lookup (`processLookupUpdateDoc`) без проверки `modifiedOn`, а `ChatViewport.handleLookupTx` применяет его и при равном `modifiedOn`. Поэтому итоги пишутся значением, а список голосовавших меняется парой `$pull {account}` + `$push`: ключи апдейта применяются по порядку. `$inc` по вложенному ключу (`votes.a`) ядро не умеет: появится поле с буквальным именем `votes.a`.
- Хеш ответа викторины - HMAC с ключом, выведенным из секрета токенов (`serverToken.metadata.Secret`). Transactor считает хеш при создании опроса, сервис activity - при голосе, поэтому секрет у них должен совпадать; после смены секрета старые викторины ответ не раскрывают. В хешируемую строку входит id воркспейса: id опроса задаёт клиент, и без воркспейса ответ можно было бы подобрать, создав такую же викторину в своём воркспейсе.

## Права

- Удаление апплета берёт привязку (`attachedTo`, `attachedToClass`, `collection`) всегда из сохранённого экземпляра: по ней `processCollection` уменьшает счётчик, и подставленная привязка уменьшила бы счётчик чужого сообщения.
- Каскад коллекций при удалении сообщения приходит в `ActivityMiddleware` с `isTriggerCtx` (`processDerivedTxes`), то есть как доверенный, а аккаунт в `ctx` остаётся удаляющим. Поэтому правило "удаляет автор или Maintainer" для прямого `TxRemoveDoc` апплета не мешает модератору удалить чужое сообщение. `modifiedBy` производной tx - не актор, а `modifiedBy` удаляемого документа.
- `TxMiddleware` пишет tx в журнал до вставки документа (`await txPromise` перед `provideTx`). Создание викторины с чужим id оставило бы в журнале хеш для каждого перебранного варианта: вставка падает на ключе, а свою tx клиент читает. Поэтому создание викторины после всех проверок пространства получает `space: core.space.DerivedTx` и в журнал не попадает, а занятый id викторины отклоняется до хеширования (`isAppletIdTaken`). Остальные tx апплетов в журнал пишутся: `lastTx` двигает только запись в журнал, и без неё переподключённый клиент получал "Reconnected" вместо "Refresh" и показывал удалённый опрос.
- `TriggersMiddleware.processCollection` берёт имя коллекции из клиентской tx, а `$inc` по нечисловому полю заменяет значение на ±1. Удаление несуществующей реакции с `attachedTo` = опрос и `collection: 'anonymous'` дало бы доверенный `$inc` флага (`anonymous` = -1 переводит следующие голоса в открытый `userVotes`). Поэтому `isCounterField` проверяет поле по сохранённому родителю (базовый `AppletInstance` из tx полей опроса не знает): объявленное поле должно быть `Collection`, необъявленное проходит, только если в нём число или пусто. Так считаются коллекции миксинов и `_reactions` рейтинга, а данные миксина (объект под id миксина) не затираются.
- Родителя `processCollection` берёт из tx и ищет без фильтра сессии. Поэтому подделанное удаление или перенос с `collection: 'applets'` уменьшает счётчик чужого сообщения в любом пространстве. Так устроены все коллекции платформы.
- Опрос неизменяем, но перенос задачи в другой проект шлёт `update(poll, { space })`: `applets` - коллекция `ActivityMessage`, и `updateIssuesOnMove`/`moveToSpace` обходят все коллекции. Такой апдейт пропускает `followsParent`, если сообщение опроса переезжает в той же пачке.
- Анонимный опрос узнаёт повторный голос только по `PollAnswer` в PersonSpace голосующего. Поэтому `ActivityMiddleware` принимает `VotePollAction` только из своего PersonSpace, как `ChunterMiddleware.onReportAction` для жалоб. Все CUD `PollAnswer` разрешены только системе и триггерам: голосующий - участник своего PersonSpace и иначе мог бы удалить ответ и проголосовать снова. Второй PersonSpace не создать: `SpacePermissionsMiddleware` запрещает CUD `PersonSpace` всем, кроме системы.
- Документы модели (`core.space.Model`) клиент с ролью User менять может: отдельной проверки роли в конвейере нет. Поэтому `ActivityMiddleware` отклоняет клиентские tx по `activity.class.Applet`: иначе автор поставил бы опросу `editable: true` и снял анонимность или сломал форму опроса для сервиса activity.
- `Poll` и `AppletInstance` лежат в одном домене, поэтому апдейт с `objectClass: AppletInstance` пишет ту же строку опроса. Middleware ищет экземпляр по базовому классу, а можно ли его менять, берёт из модели его апплета (`Applet.editable` через `context.modelDb`), а не из класса tx.
- Виды апплетов могут прийти из других плагинов со своими валидаторами, поэтому для любого вида `ActivityMiddleware` проверяет только общее: класс вида (не базовый `AppletInstance`) и своё сообщение. Интерфейс выбирает компонент по полю `applet`, а не по классу, поэтому валидатор вида обязан сверить `applet` со своим: иначе документ другого класса с `applet: Poll` нарисовался бы опросом мимо проверок опроса.
- Клиентский `TxMixin` пишет любое поле верхнего уровня (`doc[tx.mixin] = ...` в `updateMixin4Doc` и Postgres `txMixin`), а `NormalizeTx` проверяет только, что `mixin` - строка. Поэтому `ActivityMiddleware` запрещает клиентам `TxMixin` на апплеты.
- Гость без `TxAccessLevel` не может создать документ, а опрос создаётся в одном `apply` с сообщением. Без этого mixin у `AppletInstance` сервер отклонял бы сообщение гостя целиком, а черновик к этому моменту уже очищен.
- Владельцу воркспейса lookup отдаёт пересланный оригинал из приватного канала, а апплеты оригинала отсекает проверка пространства. Найденный оригинал ещё не значит доступный опрос: `AppletsList` показывает снимок `fallback`, когда при `applets > 0` не пришло ни одного экземпляра.

## Модель и хранение

- `Poll` лежит в домене родителя (`applet`). Со своим доменом у подкласса lookup `applets: AppletInstance` у сообщения его не найдёт.
- `TAppletInstance` переопределяет `attachedTo`, и переопределение теряет `@Index(Indexed)` из `TAttachedDoc`: декоратор берёт индекс только из своего класса. Поэтому индекс на переопределении объявлен заново, как у `TThreadMessage`.
- `Poll` удаляется вместе с сообщением общим каскадом коллекций (`deleteClassCollections` в `triggers.ts`). `PollAnswer` не элемент коллекции, его удаляет триггер `OnAppletRemoved` на удаление любого апплета. Удалённый экземпляр асинхронному триггеру уже не прочитать, а tx может называть базовый `AppletInstance`, поэтому триггер берёт `Applet.dependents` всех видов и ищет их по `attachedTo` (id экземпляра уникален).
- Что из апплета уходит в снимок пересылки и в уведомление, задаёт модель вида белыми списками `Applet.snapshotFields` и `summaryFields`. Список, а не исключения: секретное поле нового вида по умолчанию не утечёт в чужое пространство.
- Адаптер создаёт таблицы `applet` и `poll_answer` по `schemas.ts` вместе с `customIndexes`, но только когда создаёт саму таблицу. У таблицы, созданной раньше схемы, составных индексов не будет.
- `PollPresenter` запрашивает `PollAnswer` вместе со своим `space`. Без него Postgres берёт все ответы опроса и проверяет членство перебором таблицы `space`, с ним это два обращения по индексу (`EXPLAIN` на 200k ответов).

## Уведомления

- Счётчик `ActivityMessage.applets` поднимает серверный `TriggersMiddleware.processCollection` отдельной derived-tx. В `TxCreateDoc` сообщения счётчика ещё нет, а создание сообщения и упоминание в нём `services/notifications` строит именно из этой tx. Поэтому для create-tx `getApplets` ищет апплеты по `attachedTo`, не глядя на счётчик; счётчику верят (`trustCounter`) только апдейты сообщения и реакции.
- Inbox рисует апплеты из `notification.applets` (снимки с вопросом) и за сообщением не ходит. Пустой массив в уведомлении значит "показать нечего": превью тогда не запрашивает экземпляры.

## Клиент

- У `ChatMessage` в режиме правки черновик ввода - это сам документ сообщения, а `applets` у сообщения - счётчик. Поэтому черновики апплетов называются `appletDrafts`: под именем `applets` реактивное присваивание затёрло бы счётчик.
- Svelte 4 упорядочивает реактивные блоки только по переменным, которые блок присваивает сам. Присваивание через вызов функции (`setPending(undefined)` в `$:`) порядок не задаёт, и зависимый `$: isVoting = pending != null` выше по коду в том же проходе не пересчитывается: спиннер голоса залипает. Поэтому в `$:` у `PollPresenter` `pending` присваивается напрямую. Порядок виден в скомпилированном `$$self.$$.update`.
- Svelte 4 считает зависимостью реактивного блока и переменную, которую читает колбэк внутри него. `$: appletActions = ...` с `draftApplets` в колбэке `showPopup` пересобирал бы кнопки ввода на каждую правку черновика, поэтому колбэк вынесен в функцию вне блока (`showAppletCreate`).
- Апплет не знает сообщения вокруг себя, поэтому свои пункты контекстного меню он кладёт в `WeakMap` по самому событию (`appletContextMenu.ts`), а `ActivityMessageTemplate` их забирает. По правому клику над апплетом открывается меню только с его пунктами, без пунктов сообщения; без пунктов меню нет вовсе: `isAppletContextMenu` узнаёт апплет по записи в `WeakMap`, даже с пустым списком.
- В `PollTimeSetting` пункт "Другое время…" - подменю `popup` с `DatePicker` у `Menu` кита. Хост попапов событие `submenu` не пробрасывает, поэтому результат даты корневой `Menu` отдаёт через проп `onResult`. По `close` в `onResult` меню закрывается вручную (`popup.close()`) и `popup` сбрасывается сразу: `close()` из `showPopup` колбэк закрытия не вызывает, и кнопка осталась бы нажатой, а меню больше не открылось бы.
- Строку `activity:string:Emoji` объявляет `models/activity/src/plugin.ts`, а бандл модели грузит и `plugins/activity`, и `plugins/activity-resources/src/plugin.ts`: повторное объявление того же ключа в любом из них роняет сборку модели (`'identify' overwrites 'Emoji'`). Для подсказки кнопки эмодзи заведена своя строка `AddEmoji`.
- Сервис молча отбрасывает голос, который не может принять (вне окна, повторный, отмена без `revote`). Поэтому `PollPresenter` через 10 с без результата снимает спиннер и показывает уведомление "Голос не учтён" / "Голос не отменён".
- `Label` из `packages/ui` переводит асинхронно: пока строки плагина не загружены, первый `translateCB` ждёт загрузки, а следующий с новыми `params` уже находит строку и отвечает сразу. Поэтому в `Label` счётчик запросов: поздний ответ не перетирает свежий (число, посчитанное до загрузки данных).
- Попап результатов ищет голосовавших по `Person` (`personUuid`), а не по `employeeByAccountStore`: у гостя и деактивированного аккаунта есть персона, но нет активного сотрудника.
- Иконку на цветной плашке (`IconBox` с `color` в `AppletTile` и в строках настроек) красит `color` плашки, поэтому символ нужен с `currentColor`. Символы кита (`ui.icon.Calendar`, `ui.icon.Lock`) такие.

## Sanity-тесты формы

- Вопрос о закрытии (`CloseConfirm`) берёт заголовок той же формы: пока он открыт, `PollPage.form()` находит два диалога «Create Poll». Видимость формы проверять по `questionInput()`, кнопки вопроса брать из его `footer` (в шапке тоже есть крестик «Close»).
- Подсказка на кнопке показывается по таймеру после `mousemove`; под нагрузкой одного `hover()` бывает мало, поэтому в `polls-form.spec.ts` наведение повторяется в `toPass`.

## Sanity-тесты прав (`polls-rights.spec.ts`)

- Запись через REST-методы `createDoc`/`addCollection`/`updateCollection`/... идёт в `v1op` клиента `api-client`; раньше он отдавал `UnknownError` с `statusText` и терял `kind` отказа, который сервер кладёт в тело. Теперь он разбирает тело, как `tx()`, и 403 не повторяет.
- Голос в чужом `PersonSpace` до `ActivityMiddleware` не доходит: личное пространство приватное, `SpaceSecurityMiddleware` отвечает `NotSpaceMember`. `ForeignPrivateWrite` проверяется только юнит-тестом.

## Sanity-тесты мест опроса (`polls-places.spec.ts`)

- Канал, из которого ушли, остаётся в DOM без `inert` и Playwright считает его видимым: после пересылки опрос в исходнике ищется как регион вне `.forwarded-message`, иначе strict mode находит копию из целевого канала. `filter({ visible: true })` не помогает.
- Диалог пересылки - `.hulyModal-container` с «Forward message», а не `.antiPopup`; поле поиска `Search...`. Действия сообщения берут последнее совпадение по тексту: ответ-цитата повторяет текст исходника, поэтому пересылать до ответа.
- У `BasePreview` нет слота по умолчанию, только `content` и `right`: содержимое без `slot="content"` молча не рисуется (так терялся вопрос опроса в превью упоминания). `BaseMessagePreview` прокидывает слот по умолчанию сам.
- Канал, созданный через REST, спек открывает по URL (`openChannel`): клик ждёт, пока канал появится в навигаторе, и в CI за 30 с это не всегда успевало.
- Параллельные прогоны разных спеков чистят общий `test-results`: свой прогон запускать с `--output <scratchpad>`.
