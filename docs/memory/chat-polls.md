# Чат: опросы (апплеты)

Область: [Чат](../features/chat.md).

## Путь голоса

- `services/activity/src/worker.ts` отбрасывает tx из `DOMAIN_TRANSIENT` (bddd8ef8d1, 2026-08-12), поэтому транзиентный `VotePollAction` пропускается явным исключением. Если это исключение убрать, голоса молча перестанут доходить.
- Сервис activity применяет результат через REST `TxApplyIf`. Эхо этой tx попадает в Kafka только после ответа REST (`client.ts:311`), так что следующий голос из партиции может опередить эхо предыдущего. Поэтому `VotePollHandler` читает опрос и ответ из БД, а не из кэша, который обновляется по эху. Голоса одного воркспейса обрабатываются строго по очереди: одна партиция, `eachMessage`.
- `TxApplyIf` не одна транзакция БД: `PostgresAdapter.tx` пишет домены по очереди, каждый запрос коммитится сам, без отката. Если запись оборвалась после `PollAnswer`, повтор REST с тем же телом падает на первичном ключе ответа и до опроса не доходит. Поэтому сервис досчитывает голос при передоставке из Kafka: голос с уже записанным ответом и отмена без ответа пересчитывают итоги по `PollAnswer` (`syncWithAnswers`). Считать по `{ options: id }` в запросе нельзя: `escape()` адаптера выкидывает из значения символы вне `[A-Za-z0-9_.:\-$ ]` и кириллицы.
- Пересчёт по ответам запускается, только когда голос правда оборван: ответ новее опроса по `modifiedOn` (сервис пишет ответ первым), а для отмены - если `total` ответов не сходится с `totalVotes`. Иначе повторный голос гостя в цикле читал бы все ответы большой викторины на каждом сообщении партиции.
- Если обработчик в `services/activity` бросает ошибку, Kafka повторяет сообщение бесконечно и держит всю партицию. Поэтому всё, что клиент присылает в `VotePollAction`, проверяется по типам дважды: в middleware и в обработчике. Опрос, сломанный в хранилище, обработчик пропускает, а не падает.
- Апдейт опроса от сервиса должен быть идемпотентным. Live query применяет апдейт к документам из lookup (`processLookupUpdateDoc`) без проверки `modifiedOn`, а `ChatViewport.handleLookupTx` применяет его и при равном `modifiedOn`. Поэтому итоги пишутся значением, а список голосовавших меняется парой `$pull {account}` + `$push`: ключи апдейта применяются по порядку. `$inc` по вложенному ключу (`votes.a`) ядро не умеет: появится поле с буквальным именем `votes.a`.
- Хеш ответа викторины - HMAC с ключом, выведенным из секрета токенов (`serverToken.metadata.Secret`). Transactor считает хеш при создании опроса, а сервис activity - при голосе, поэтому секрет у них должен совпадать. После смены секрета старые викторины ответ не раскрывают. В хешируемую строку входит id воркспейса: id опроса задаёт клиент, и без воркспейса ответ можно было бы подобрать, создав такую же викторину в своём воркспейсе.

## Права

- Каскад коллекций при удалении сообщения приходит в `ActivityMiddleware` с `isTriggerCtx` (`processDerivedTxes`), то есть как доверенный, а аккаунт в `ctx` остаётся удаляющим. Поэтому правило "удаляет автор или Maintainer" для прямого `TxRemoveDoc` апплета не мешает модератору удалить чужое сообщение. `modifiedBy` производной tx - не актор, а `modifiedBy` удаляемого документа.
- `TxMiddleware` пишет tx в журнал до вставки документа (`await txPromise` перед `provideTx`). Создание викторины с id чужой оставляло бы в журнале хеш для каждого перебранного варианта: вставка падает на ключе, а свою tx клиент читает. Поэтому клиентские tx апплетов помечаются `space: core.space.DerivedTx` после всех проверок пространства и в журнал не попадают, а занятый id отклоняется до хеширования.
- `TriggersMiddleware.processCollection` брал родителя и имя коллекции из клиентской tx. Удаление несуществующей реакции с `attachedTo` = опрос и `collection: 'anonymous'` давало доверенный `$inc` поля (`anonymous` = -1 переводит следующие голоса в открытый `userVotes`), а с `collection: 'applets'` - уменьшало счётчик чужого сообщения в любом пространстве: триггер ищет родителя без фильтра сессии. Теперь имя сверяется с атрибутом класса сохранённого родителя (базовый `AppletInstance` из tx полей опроса не знает), а родитель берётся из удалённого документа (`removedMap`, его заполняет `DomainTxMiddleware` до триггеров) или из документа, прочитанного до апдейта переноса.
- Опрос неизменяем, но перенос задачи в другой проект шлёт `update(poll, { space })`: `applets` - коллекция `ActivityMessage`, и `updateIssuesOnMove`/`moveToSpace` обходят все коллекции. Такой апдейт пропускает `followsParent`, если сообщение опроса переезжает в той же пачке.
- Анонимный опрос узнаёт повторный голос только по `PollAnswer` в PersonSpace голосующего. Поэтому `ActivityMiddleware` принимает `VotePollAction` только из своего PersonSpace, как `ChunterMiddleware.onReportAction` для жалоб. Все CUD `PollAnswer` разрешены только системе и триггерам: голосующий - участник своего PersonSpace и иначе мог бы удалить ответ и проголосовать снова. Создать себе второй PersonSpace нельзя: `SpacePermissionsMiddleware` запрещает CUD `PersonSpace` всем, кроме системы.
- `Poll` и `AppletInstance` лежат в одном домене, поэтому апдейт с `objectClass: AppletInstance` пишет ту же строку опроса. Middleware ищет экземпляр по базовому классу, а можно ли его менять, берёт из модели его апплета (`Applet.editable` через `context.modelDb`), а не из класса tx.
- Клиентский `TxMixin` пишет любое поле верхнего уровня (`doc[tx.mixin] = ...` в `updateMixin4Doc` и Postgres `txMixin`), а `NormalizeTx` проверяет только, что `mixin` - строка. Поэтому `ActivityMiddleware` запрещает клиентам `TxMixin` на апплеты.
- Гость без `TxAccessLevel` не может создать документ, а опрос создаётся в одном `apply` с сообщением. Без этого mixin у `AppletInstance` сервер отклонял бы сообщение гостя целиком, а черновик к этому моменту уже очищен.
- Владельцу воркспейса lookup отдаёт пересланный оригинал из приватного канала, а апплеты этого оригинала отсекает проверка пространства. Значит, найденный оригинал ещё не значит доступный опрос: `AppletsList` показывает снимок `fallback`, когда при `applets > 0` не пришло ни одного экземпляра.

## Модель и хранение

- `Poll` лежит в домене родителя (`applet`). Если дать подклассу свой домен, lookup `applets: AppletInstance` у сообщения его не найдёт.
- `TAppletInstance` переопределяет `attachedTo`, и переопределение теряет `@Index(Indexed)` из `TAttachedDoc`: декоратор берёт индекс только из своего класса. С тех пор как `Poll.question` в полнотекстовом индексе, без этого у документа опроса в Elastic не было бы `attachedTo`, и поиск с вложенными документами не связал бы его с сообщением. Поэтому индекс на переопределении объявлен заново, как у `TThreadMessage`.
- `Poll` удаляется вместе с сообщением общим каскадом коллекций (`triggers.ts:395`). `PollAnswer` не элемент коллекции, его удаляет триггер `OnPollRemoved` на удаление любого апплета.
- Адаптер создаёт таблицы `applet` и `poll_answer` по `schemas.ts` вместе с `customIndexes`, но только когда создаёт саму таблицу. У таблицы, созданной раньше схемы, составных индексов не будет.
- `PollPresenter` запрашивает `PollAnswer` вместе со своим `space`. Без него Postgres берёт все ответы опроса и проверяет членство перебором таблицы `space`, а с ним это два обращения по индексу. Проверено `EXPLAIN` на 200k ответов.

## Уведомления

- Счётчик `ActivityMessage.applets` поднимает серверный `TriggersMiddleware.processCollection` отдельной derived-tx. В `TxCreateDoc` сообщения счётчика ещё нет, поэтому `handleCreateMessage` в `services/notifications` для сообщения без текста и вложений ищет апплеты по `attachedTo` (`getApplets(..., true)`). У сообщения с текстом снимки приходят с апдейтом контекстов по этой tx.
- Inbox рисует апплеты из `notification.applets` (снимки с вопросом) и за сообщением не ходит. Пустой массив в уведомлении значит "показать нечего": превью тогда не запрашивает экземпляры.

## Клиент

- У `ChatMessage` в режиме правки черновик ввода - это сам документ сообщения, а `applets` у сообщения - счётчик. Поэтому черновики апплетов называются `appletDrafts`: под именем `applets` реактивное присваивание затёрло бы счётчик.
- Svelte 4 упорядочивает реактивные блоки только по переменным, которые блок присваивает сам. Присваивание через вызов функции (`setPending(undefined)` в `$:`) порядок не задаёт, и зависимый `$: isVoting = pending !== undefined` выше по коду в том же проходе не пересчитывается: спиннер голоса залипает. Порядок можно проверить по скомпилированному `$$self.$$.update`.
- Svelte 4 считает зависимостью реактивного блока и переменную, которую читает колбэк внутри него. `$: appletActions = ...` с `draftApplets` в колбэке `showPopup` пересобирал бы кнопки ввода на каждую правку черновика. Такие колбэки выносятся в функцию вне блока.
- Апплет не знает сообщения вокруг себя, поэтому свои пункты контекстного меню он кладёт в `WeakMap` по самому событию (`appletContextMenu.ts`), а меню сообщения в `ActivityMessageTemplate` их забирает. Если показать свой `Menu` с `stopPropagation`, пропадут "Ответить", "Переслать" и "Удалить".
- `DatePopup` с `withTime`: `MonthSquare` переносит часы и минуты в выбранный день, но клик по дню закрывал окно через `closeDP()` без `withTime`, и `convertToDay` превращал дату в полдень UTC. Теперь клик закрывает с `withTime`, и время из полей сохраняется. Это поведение всех выборов даты со временем, не только опроса.
- `ModernDropdown` после выбора пункта держит свой `selected` и не сбрасывает его по пропу, пока значение пропа не изменится. Пункт "Другое время…" открывает выбор даты, который можно отменить, поэтому в `PollTimeSetting` своя кнопка с `ModernPopup`.
