# Threads: сортировка списка и lastReply

Область: [Чат](../features/chat.md)

- Сортировка по `$lookup.<field>.<attr>` в Postgres идёт по колонке присоединённой таблицы, если это колонка. Поле из jsonb `data` (так было с `lastReply`) `buildOrder` не распознаёт (атрибут ищется на классе запроса, а не на классе lookup): оно сравнивается как текст, и при `DESC` `NULL` оказываются сверху. Поле, по которому сортирует список, выносим в колонку (`schemas.ts` + миграция в `services/db-migrator`), а не чиним в `buildOrder`.
- Проверять частичный индекс в `BEGIN ... ROLLBACK` бесполезно: индекс, созданный в той же транзакции, планировщик не берёт даже при `enable_seqscan=off` (`indcheckxmin`), и кажется, что индекс не подходит под запрос. Проверять нужно в отдельной базе: `CREATE DATABASE`, `pg_dump -t activity -t collaborator | psql`, затем миграция и `ANALYZE`. На dev-базе запрос Threads с новым индексом занимает <1 мс вместо ~14 мс с seq scan. Условие `replies >= 1` из запроса планировщик выводит из `WHERE replies > 0` индекса.
- `OnThreadMessageDeleted` был пустым (`TODO: FIXME`) с коммита глобальных аккаунтов `2c64ceadb8`: `createdBy` стал socialId, а старый код переводил его в Person поштучно. Теперь он пересчитывает `lastReply` и `repliedPersons` через пакетный `getPersonsBySocialIds` (server-plugins/contact). Порядок `repliedPersons` задаётся порядком первого ответа, как при `$push` в `OnThreadMessageCreated`, иначе аватарки перескакивают.
- После выноса в колонку пропало время «Last reply»: `findAll` с `lookup` разбирал строку через `getSchema(row._class)`, а `domainSchemas` проиндексирован по доменам. Для класса находилась `defaultSchema`, и `bigint` из Postgres оставался строкой. `new Date("1790671315240")` даёт `NaN`, а `TimeSince` на ложном значении ничего не выводит. `replies` приходил строкой `"4"` с тех пор, как его вынесли в колонку, но это не было заметно: строка выводится как есть, а `> 0` работает через приведение. Колонки прямого `lookup` к числу приводились только для `createdOn`/`modifiedOn`. Теперь `parseLookup` берёт схему домена, lookup-колонки приводятся по схеме присоединённой таблицы (`storage.ts`, тест `parseLookup.spec.ts`). Без `lookup` строка идёт через `parseDocWithProjection(domain)`, и там всё было правильно.
- Сбросить колонку можно через `$unset`: у update с оператором адаптер применяет `TxProcessor.applyUpdate` к документу и пишет колонку из результата, то есть `NULL`.
- В режиме «по дате создания» `liftThread` не поднимает тред, родитель которого старше загруженной страницы: такой тред встал бы в конец списка вне своей страницы.
