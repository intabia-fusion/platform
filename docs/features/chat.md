# Чат

> Сверено с кодом: коммит 94bd827fd9, 2026-09-25.

Внутренний чат платформы: каналы, direct-сообщения, треды, загрузка окна сообщений, чтение при скролле, навигатор с бейджами непрочитанного, поиск. Сущности: `Channel`/`DirectMessage` (пространства чата), `ChatMessage`/`ThreadMessage` (сообщения), `Chat` (личное состояние pin/hidden). Непрочитанное и уведомления хранятся в `DocNotifyContext`/`ReadState` - их модель, сервис-генератор, inbox, push и email описаны в [notifications.md](notifications.md); здесь - только то, как чат их читает и показывает.

## Как работает

1. **Создание DM с дедупликацией.** Клиент `createAndGetDirect`/`findExistingDirect` сначала ищет существующий DM по составу участников (plugins/chunter/src/utils.ts) -> при создании `ChunterMiddleware.onDirectCreate` на сервере считает `referenceId = sha256(sorted members)`, форсирует `private=true/archived=false/autoJoin=false`, добавляет автора в members (но не `systemAccountUuid`, иначе группа обходит дедуп) и возвращает `Forbidden`, если DM с таким `referenceId` уже существует (только для 1:1, `members.length <= 2`) - server-plugins/chunter/src/middleware.ts. Изменение `referenceId`/`private`/`type` у DM запрещено всегда; изменение `members` запрещено, если у DM уже есть `referenceId` или `type: 'person'` - `onDirectUpdate`.
2. **Открытие канала -> окно сообщений.** `Channel.svelte` берёт `hasUnread` из `unreadByDoc`, запрашивает `ReadState` (не дожидаясь) и получает `ChatViewport.getOrCreate(readState, attachedTo, selectedMessageId, limit=50, isThread, hasUnread)` - plugins/chunter-resources/src/chatViewport.ts. `initializeViewport` одним `Promise.all` грузит последнюю страницу (`limit+1`, `createdOn desc`), ждёт `ReadState` и, при deep-link, целевое сообщение. Без цели `resolveUnreadAnchor` ищет первое непрочитанное чужое сообщение (`createdBy $nin me.socialIds`, позже `ReadState[me].timestamp`; локально по загруженной странице, иначе отдельный `findOne`). Если анкор старше последней страницы - `loadAnchoredStart` грузит окно `limit/2` назад и вперёд от него; иначе `applyLatestTail` и live-хвост `subscribeToLiveTail` через `createQuery`. `newTimestamp` = `createdOn` анкора - позиция разделителя "New".
3. **Скролл и подгрузка.** `ReverseChannelScrollView.svelte`: `initializeScroll` скроллит к сообщению, к разделителю "New" (`newSeparatorOffset=150`) или к низу; подгрузка вверх/вниз при `loadMoreThreshold=200` px через `viewport.loadMore` (`loadMoreInternal`/`queryHistoryChunk`: курсор по `createdOn` с `$lte/$gte`, дубли на границе вычищает `getBoundaryOverlapIds`, при пустой странице - fallback на строгое неравенство). Любой ответ, пришедший после `resetViewport`, отбрасывается (`viewportVersion`/`StaleVersionError`). Кнопка "Latest messages" -> `jumpToEnd`; `JumpToDateSelector` -> `jumpToDate`; смена `selectedMessageId` -> `jumpToMessageId` (fast path, если сообщение уже загружено).
4. **Живые обновления.** `ChatViewport.handleTransactions` (`addTxListener`) патчит загруженные сообщения/реакции/вложения локально через `TxProcessor.updateDoc2Doc`, при `tx.modifiedOn` старше текущего - рефетч; новые сообщения приходят через live-хвост, `ReverseChannelScrollView` доскролливает, если пользователь у низа (`shouldScrollToNew`, `|scrollTop| < 100`).
5. **Чтение при скролле.** `readViewportMessages` (plugins/chunter-resources/src/scroll.ts) собирает видимые сообщения по `getBoundingClientRect`, дебаунс 500 мс на чат (`immediate` при закрытии вью); параллельно `IntersectionObserver` в `ReverseChannelScrollView` (`observeMessage`/`flushReadQueue`, тоже 500 мс). Оба зовут `readMessages`: `ReadState[me] = {messageId, timestamp}` только если timestamp больше сохранённого (`lastViewTimestampStore`), плюс `ReadNotificationAction` с `reactionIds` попавших во вьюпорт сообщений. Сервер валидирует запись (`NotificationMiddleware`), сервис уведомлений снимает непрочитанное (`module/read.ts`). `recheckNotifications` досылает `ReadNotificationAction`, если контекст обновился позже, чем пользователь прочитал сообщение (`chatReadMessagesStore`).
6. **Открытый чат считается читаемым.** Пока `isReadingTail` (окно сфокусировано, скролл у низа `|scrollTop| < 50`, хвост загружен) - `inboxClient.setDocReading(object._id, true, reader)`; `reader` различает главную панель и сайдбар. Раз в `forceReadPauseMs=3000` при ненулевом `unreadMessagesCount` вызывается `forceReadDocState` - подчищает расхождение с сервисом. - plugins/chunter-resources/src/components/ReverseChannelScrollView.svelte.
7. **Кэш вьюпортов.** `ChatViewport` держит раздельные LRU-кэши каналов и тредов (`MAX_CACHE_SIZE=10`, `TTL_MS` 15 минут, проверка раз в 5 минут); активные (`acquire`/`release`) не вытесняются; при повторном открытии unread-маркер пересчитывается по свежему `ReadState` (`syncUnreadMarker`). - plugins/chunter-resources/src/chatViewport.ts.
8. **Навигатор.** Секции в `chatNavGroupModels` (plugins/chunter-resources/src/components/chat/utils.ts), порядок везде по времени последнего сообщения: запрос `Chat` джойнит `readState` (`lookup`, проекция только `latestMessageTimestamp` и `attachedToClass`, иначе пришли бы позиции чтения всех участников; класс нужен клиентскому `match` чата, добавленного вживую) и сортирует на сервере по `$lookup.readState.latestMessageTimestamp` (новее первым, без сообщений - 0, в конце); клиент не пересортировывает: LiveQuery при изменении `latestMessageTimestamp` в readState сам переставляет результат (`handleDocUpdateLookup`). Окно секции activity (`limit` 5 на класс): чат, которого в окне нет, LiveQuery поднимает по одному запросу `Chat` по ссылке `readState` (индекс `chunter_doc_readState__index`), и только если новое время заходит за край окна; запрос фильтрует `$lookup.readState.attachedToClass` по потомкам класса секции, а Tx состояния несёт `attachedTo/attachedToClass`, так что состояние канала окно задач не трогает (см. notifications.md "Права записи", docs/memory/postgres-lookup-projection.md). Чат без состояния этот фильтр не проходит и не показывается, пока состояния нет. Секция starred (`wrap: false`) склеивает ответы запросов по классам и сортирует склейку по тому же времени, каналы и личные сообщения вместе; группа activity `deferred: true` - грузится после остальных. Бейдж `ChatNavItem.svelte`: число `unreadMessagesCount`, цвет `notifiedMessagesCount === 0 ? gray : red`; свёрнутая секция показывает сумму. Маркер приложения "Чат" - `ShowNotifyMarkerFn` (plugins/chunter-resources/src/index.ts) с учётом `showChatBadge`. Счётчик Threads - `unreadThreadsCountStore` (plugins/chunter-resources/src/stores.ts): контексты с `notifiedMessagesCount > 0`, чей `objectClass` - `ActivityMessage`.
9. **Скрытый чат получает сообщение -> auto-unhide.** `ChunterMiddleware.tx` (server-plugins/chunter/src/middleware.ts): на `TxCreateDoc<DocNotifyContext>` с непустыми `unreadMessages` и `latestNotifications`, либо на `TxUpdateDoc` с `$push` `message`-уведомления в `latestNotifications` (`combineAttributes`) ищет скрытые `Chat` по объекту (`getHiddenChats`, кэш `hiddenChats`) и шлёт `getUnhideChatsTx` через `derived.tx`. Т.е. чат "выныривает" в момент создания уведомления, а не сырой Tx сообщения; mention тоже попадает в `unreadMessages`, поэтому раскрывает чат.
10. **Auto-hide неактивных чатов.** `OnUserStatus` -> `syncChat` (server-plugins/chunter-resources/src/index.ts): раз в `updateChatInfoDelay` (24 ч) на пользователя (`ChatSyncInfo`), коалесинг реконнектов `syncChatCoalesceMs=60 с`, `RateLimiter(4)`; скрывает не-pinned `Chat` документов (не наследников `ChunterSpace`: каналы и директы не скрываются), у которых `ReadState.latestMessageTimestamp` старше `hideDelay` (14 дней) и нет notified-непрочитанного (`UnreadMessageId.notified` / `UnreadMessageChunk.notifiedCount`). Разовый проход по всем чатам - миграция `hide-inactive-chats-v1` (models/notification/src/migration.ts), тоже без директов. Директы, которые она скрыла раньше, возвращает `unhide-auto-hidden-directs-v1` (models/chunter/src/migration.ts); скрытые пользователем (последняя `TxUpdateDoc` с `hidden` - `true` и после неё в директе нет сообщений) остаются скрытыми. Транзакции триггеров и `ChunterMiddleware` производные (`DerivedTx`) и в `DOMAIN_TX` не пишутся, поэтому ни системное скрытие, ни auto-unhide следа не оставляют.
11. **Поиск по сообщениям.** `createChatSearchStore` шлёт полнотекстовый запрос (`searchIn: ['content']`, `PAGE_SIZE=50`) с курсором и счётчиком `generation`, отбрасывающим ответы устаревших запросов - plugins/chunter-resources/src/search/store.ts. Для DM `ChunterMiddleware.findAll` добавляет `'*'`-префикс к `$search`, если он не задан явно. Основной текст в индексе: `ChatMessage.message` и `Channel.description` (`contentField`, `models/server-chunter/src/index.ts`), у сообщения к нему добавляются вопросы его опросов (`contentCollections: ['applets']`); у DM текста в индексе нет, его находят по именам участников в `searchTitle`. Навигатор чатов (`ChatNavigator`, `ChatNavGroup`) и список `ChatsList` ищут только по заголовку и идентификатору: `$searchIn: ['title', 'identifier']`.

## Фичи

### Ядро чата

- **Каналы как пространства.** `TChannel extends TChunterSpace extends TSpace`, `topic` под FullText-индексом, скрытые `icon`/`emoji`. - models/chunter/src/types.ts.
- **DM и групповые диалоги.** `TDirectMessage` - вариант ChunterSpace с readonly `type: 'person'|'group'` (>2 участников = группа). - models/chunter/src/types.ts.
- **Server-дедупликация 1:1 DM через referenceId.** SHA-256 отсортированных members, `Forbidden` при повторе; действует только для DM из 2 участников. - `ChunterMiddleware.onDirectCreate`, `getMembersHash`, server-plugins/chunter/src/middleware.ts; тест server-plugins/chunter/src/__tests__/direct-create.spec.ts.
- **Защита неизменяемости DM.** `referenceId`/`private`/`type` менять нельзя никогда; `members` - нельзя, если у DM есть `referenceId` или `type: 'person'`. - `ChunterMiddleware.onDirectUpdate`, server-plugins/chunter/src/middleware.ts.
- **Права на сообщение на сервере.** Для клиентских tx `ChatMessage` и наследников (`ThreadMessage`, комментарии документов, сообщения AI) `ChunterMiddleware.onMessageChange` повторяет правила интерфейса. Проверяется любая tx домена сообщений: хранилище пишет её по `_id`, какой бы класс она ни называла, поэтому правило решает по классу сохранённого документа. Документ ищется через `lowLevelStorage` без фильтра пространств сессии: сообщение из чужого приватного канала тоже защищено.
  - удалить сообщение может автор или роль Maintainer и выше (`canDeleteMessage` в интерфейсе);
  - менять содержимое и привязку (`message`, `attachments`, `editedOn`, `forwardedMessage`, `forwardContent`, `attachedTo`, `objectId`, `space`, счётчик `applets` и т.п., в том числе через `$unset`/`$rename`) может только автор, владелец воркспейса тоже нет;
  - чужое сообщение переезжает только вместе со своим родителем: апдейт из одного `space` допустим, если в той же пачке родитель (`attachedTo`, та же таблица) переезжает в то же пространство. Так перенос задачи (`moveIssueToSpace`) и общий `moveToSpace` уносят комментарии и ответы других людей. Сообщение, прицепленное прямо к пространству (канал, директ), так не переезжает (`followsParent` в server-plugins/activity/src/middleware.ts);
  - остальные поля открыты участникам: закрепление `isPinned`, `resolved` у комментариев документов, `applied`/`project` у предложений AI;
  - `createdBy`/`createdOn` не меняет никто: по ним проверяется автор;
  - `TxMixin`, чей `mixin` не класс-миксин, запрещён: адаптер записал бы поле с этим именем, например `message`.

  Системный аккаунт и триггеры (`isTriggerCtx`) не проверяются: каскад удаления сообщения уносит чужие ответы треда. Автор - `createdBy` сохранённого сообщения, актор - аккаунт сессии. - server-plugins/chunter/src/middleware.ts; тест server-plugins/chunter/src/__tests__/message-rights.spec.ts.
- **Переход в DM с персоной.** Клик по упоминанию сотрудника (в тексте сообщения - через `contact.component.EmployeePresenter` inline, а не голый `ObjectMention`) и по ссылке на сотрудника внутри приложения chunter открывает DM, а не карточку персоны; кнопки "Сообщение"/"Позвонить" (`contact.extension.EmployeePopupActions`) есть и в тултипе, и в заголовке карточки персоны (`PersonHeaderActions` на `view.extensions.EditDocTitleExtension`); в шапке 1:1 DM - кнопка перехода в карточку и точка расширения `chunter.extensions.DirectHeaderExtension` (props `{ employee }`), куда love кладёт `InviteEmployeeButton` (звонок как в офисе; скрыт для себя и AI-бота, заблокирован, если нет миксина Employee или `active !== true`). - `openDirectForPerson`, plugins/chunter-resources/src/utils.ts; packages/presentation/src/components/markup/ObjectNode.svelte; plugins/contact-resources/src/components/PersonElement.svelte, `person/PersonHeaderActions.svelte`; plugins/chunter-resources/src/components/ChannelHeader.svelte.
- **URL канала и директа.** `path[3]` любого `ChunterSpace` - `<имя>-<id>` без `|<class>` (`view.mixin.LinkIdProvider` на `ChunterSpace`/`Channel`/`DirectMessage`: `getChunterSpaceLinkId`/`parseChunterSpaceLinkId`); у модельных каналов `:` заменяется на `-` (`chunter:space:General` -> `chunter-space-General`). Без `|` класс декодируется как `ChunterSpace`, конкретный берётся из загруженного документа. Прочие документы в чате - по-прежнему `<id>|<class>`; старые ссылки `<id>|<class>` открываются. - `encodeChatURI`/`openChunterSpace`, plugins/chunter-resources/src/navigation.ts; `decodeChatURI`/`toChunterSpaceLinkId`/`parseChunterSpaceLinkId`, plugins/chunter-resources/src/linkId.ts (тест `__tests__/linkId.test.ts`); models/chunter/src/index.ts. В аналитику URL уходит без имени: `stripLinkSlugs`, packages/ui/src/location.ts.
- **Ссылка на канал.** Пункт "Копировать ссылку" в контекстном меню канала в навигаторе (`getLink` -> `GetChunterSpaceLinkFragment`). - plugins/chunter-resources/src/components/chat/navigator/ChatNavItem.svelte.

### Опросы (апплеты)

- **Создание.** Кнопка апплета в `ChatMessageInput` открывает его `createComponent` (`CreatePoll`). Черновик лежит в `draftApplets` и в черновике сообщения (`appletDrafts`), превью черновика - `PollPreview`. При отправке `createFn` (`createPoll`) создаёт `Poll` в том же `client.apply`, что и сообщение. Счётчик `applets` сообщения поднимает `TriggersMiddleware.processCollection` отдельной derived-tx. При правке сообщения кнопок апплетов нет. Гость тоже создаёт апплеты (`TxAccessLevel` у `AppletInstance`), как сообщения и вложения.
  - "Можно отменить голос" (`revote`): по умолчанию включено, у викторины выключено.
  - "Отложенный старт" и "Ограничить срок" (`PollTimeSetting`): пресет 1/3/8/24/72 ч или точное время. Пресет хранится в черновике как `startDelay`/`duration`, а в `startAt`/`endAt` превращается только при отправке (`resolvePollTimes`). Поэтому такой черновик не устаревает. Если точное время окончания уже прошло или раньше начала, превью черновика предупреждает об этом (`getPollTimeError`), а `ChatMessageInput` с этого момента не отправляет сообщение (`getAppletDraftExpiry`, `disableSubmit`): сервер отклонил бы всю пачку, а черновик к тому времени уже стёрт.
  - Лимиты `pollLimits` (plugins/activity): до 10 вариантов, вопрос до 300 символов, вариант до 100. Форма их держит (`limit` у полей, новый пустой вариант не добавляется сверх лимита), сервер проверяет.

  Файлы: plugins/chunter-resources/src/components/chat-message/ChatMessageInput.svelte, plugins/activity-resources/src/{poll,pollTime}.ts.
- **Проверка при создании.** `ActivityMiddleware.validatePollCreate`:
  - вопрос и не меньше двух вариантов с уникальными id и непустыми подписями;
  - режим `single`/`multiple`, конец позже начала, `revote` - флаг;
  - у викторины один ответ, правильный вариант среди вариантов, без `revote`;
  - опрос попадает только в своё сообщение: либо существующее, автор которого - текущий пользователь, либо создаваемое в той же пачке раньше опроса. Пространство опроса совпадает с пространством сообщения. Привязка берётся так же, как её возьмёт хранилище: вся из tx, если tx называет сообщение, иначе вся из атрибутов. Других видов апплетов клиент не создаёт;
  - id опроса не занят (поиск без фильтра пространств), иначе хеш посчитался бы для id чужой викторины;
  - автор - отправитель: `createdBy` из tx стирается, `IdentityMiddleware` проверяет только `modifiedBy`.

  Middleware обнуляет итоги и заменяет `quizAnswer` на `quizAnswerHash`: HMAC-SHA256 от `воркспейс:опрос:вариант` с ключом, выведенным из секрета токенов. Клиентские tx апплетов (создание, правка, удаление) он помечает `space: core.space.DerivedTx`, и `TxMiddleware` не пишет их в журнал: создание, отклонённое хранилищем, иначе оставило бы там хеш для перебора ответа. Системный аккаунт проходит без проверок. - server-plugins/activity/src/middleware.ts.
- **Права после создания.**
  - Клиентский `TxMixin` на апплет запрещён: адаптер применяет его как `doc[mixin] = ...` в обход остальных проверок.
  - Отправленный апплет можно менять, только если это разрешает его модель (`Applet.editable`). Опрос менять нельзя: его итоги и раскрытый ответ пишет только сервис activity. Где правка разрешена, менять может только автор и только поля апплета. Привязку к сообщению, вид апплета и операторы (`$inc`, `$push`, пути через точку) менять нельзя (`validateAppletUpdate`).
  - Апплет любого автора переезжает вместе со своим сообщением: апдейт из одного `space` проходит, если в той же пачке сообщение переезжает туда же (`followsParent`). Иначе перенос задачи с опросом в комментарии отклонялся бы целиком.
  - Удалить апплет отдельно от сообщения может его автор или роль Maintainer и выше, как сообщение в интерфейсе (`validateAppletRemove`). Голому `removeDoc` middleware дописывает привязку из сохранённого экземпляра, чтобы триггеры уменьшили счётчик сообщения. Каскад при удалении сообщения приходит из триггеров (`isTriggerCtx`) и не проверяется.
  - Счётчик коллекции триггеры поднимают только для коллекции: `TriggersMiddleware.isCounterField` сверяет имя с атрибутом класса сохранённого родителя. Иначе удаление несуществующей реакции с `collection: 'anonymous'` сделало бы доверенный `$inc` любого поля опроса или сообщения.
  - Родителя и коллекцию счётчика триггеры берут из сохранённого документа, а не из tx: при удалении - из удалённого (`removedMap`), при переносе - из прочитанного до апдейта (`findMovedDocs`). Удаление или перенос несуществующего документа счётчики не трогает. Иначе любой участник канала уменьшал бы `applets` чужого сообщения в любом пространстве, и опрос пропадал бы из тредов, inbox и поиска. - foundations/server/packages/middleware/src/triggers.ts.
  - Апдейт с `objectClass: AppletInstance` проверяется по виду самого экземпляра, а опрос, созданный под `AppletInstance`, отклоняется.
  - `PollAnswer` создаёт, меняет и удаляет только система: иначе анонимный опрос принял бы повторный голос.
- **Голос.** Клиент создаёт транзиентный `VotePollAction` в своём PersonSpace. Middleware принимает голос только оттуда, проверяет типы полей и ставит `account` сессии. Кривой голос уронил бы сервис, а Kafka повторяла бы сообщение бесконечно. `services/activity` пропускает этот класс мимо фильтра `DOMAIN_TRANSIENT` (worker.ts). Дальше `VotePollHandler`:
  1. читает опрос из БД, а не из кэша;
  2. проверяет доступ к пространству опроса;
  3. проверяет окно времени по `modifiedOn` tx, который ставит transactor;
  4. применяет результат через REST `TxApplyIf` от системы с условием "опрос существует".

  Что пишется:
  - итоги - значением: `totalVotes` (число голосовавших) и `votes` (по вариантам);
  - неанонимный опрос - своя запись в `userVotes` (`{ account, options }`) парой `$pull`/`$push`, апдейт идемпотентен и не растёт с числом голосовавших;
  - анонимный опрос и викторина - `PollAnswer` в PersonSpace голосующего, у викторины - с правильным вариантом.

  Голос вне окна и повторный голос игнорируются. Чтобы сменить ответ, голос отменяют (`retract`) и голосуют заново. Отмена принимается только при `revote`, в викторине - никогда.

  `PollAnswer` и опрос пишутся разными запросами, не одной транзакцией. Если запись оборвалась между ними, Kafka передоставит голос, и сервис его досчитает (`syncWithAnswers`): пересчитает итоги по всем `PollAnswer` опроса и допишет голосующего неанонимной викторины в `userVotes`. Пересчёт идёт, только если запись правда оборвалась: голос с ответом новее опроса (`modifiedOn`) или отмена анонимного голоса, когда число ответов (`total`) не сходится с `totalVotes`. Id ответа детерминированный (хеш опроса и PersonSpace), так что второй ответ того же голосующего упадёт на ключе. - services/activity/src/poll.ts.
- **Окончание викторины.** Клиент, у которого на экране завершённая викторина без `quizAnswer`, шлёт `VotePollAction` с `reveal: true`. После `endAt` сервис пишет правильный вариант в опрос. Пока ответа нет, запрос повторяется раз в `QUIZ_REVEAL_RETRY_MS` (30 с), не больше 10 раз за сессию: часы клиента могут спешить. - `requestQuizReveal`, plugins/activity-resources/src/poll.ts.
- **Отображение.**
  - `ChatMessagePresenter` рисует `AppletsList`. Тот берёт `$lookup.applets` (окно чата `ChatViewport.LOOKUP`, `Activity.svelte`). Если lookup нет, а `applets > 0`, он сам запрашивает экземпляры: так бывает в тредах, сохранённых, закреплённых и попапах.
  - `PollPresenter` показывает статус "Начнётся через 20 минут", "Завершится через 3 часа" или "Завершён", точное время - в подсказке. Статус обновляется раз в минуту, а от двух суток до события - раз в час. В момент начала и конца он переключается сам.
  - Результаты (проценты, попап) видны после своего голоса или после окончания опроса. Опрос только для чтения (снимок, архивный канал, гость только для чтения) показывает проценты сразу, кроме незавершённой викторины: они подсказали бы ответ.
  - Текстовые превью и цитата ответа показывают иконку и заголовок через `getTitleFn` (`AppletsPreview`).
  - Пересланное сообщение показывает живой исходный опрос, если исходное сообщение доступно. Иначе показывается снимок `forwardContent.applets` только для чтения. Если исходное сообщение пришло, а его опросы нет, `AppletsList` показывает тот же снимок (`fallback`). Так бывает у владельца воркспейса: lookup отдаёт ему сообщение, но не его опросы.
  - Снимок собирает `getForwardData` (forwardData.ts) с помощью `toAppletSnapshot` из plugins/activity. В `AppletSnapshot` нет привязки к сообщению, `userVotes` и ответа викторины. Вложения пересылаются как `AttachmentSnapshot`.
  - Пункты опроса ("Отменить голос" - только при `revote`, "Показать результаты") показываются первыми в контекстном меню сообщения. Опрос кладёт их в событие (`addAppletContextActions`, appletContextMenu.ts), а `ActivityMessageTemplate` их забирает.
- **Уведомления.** Уведомления о сообщении, упоминании и реакции несут `applets` - короткие снимки (`toAppletSummary`): вопрос опроса без вариантов, итогов, голосовавших и ответа викторины. Уведомление копируется каждому получателю. Inbox показывает их без запросов: `MessageNotificationPresenter`, `ReactionNotificationPresenter`, `MentionNotificationPresenter` и `ThreadNotificationPresenter` передают снимки в превью. У сообщения с текстом снимки приходят с апдейтом счётчика (`handleUpdateMessage`). У сообщения, где только опрос, `handleCreateMessage` сам запрашивает экземпляры, потому что счётчика ещё нет; push такого сообщения - "Отправил(а) Опрос". - services/notifications/src/module/message.ts, `getApplets` в utils/misc.ts.
- **Поиск.** `Poll.question` - FullText. `SearchPresenter` у `ChatMessage` перечисляет `applets` в `contentCollections`, и индексатор дописывает текст апплетов в `fulltextSummary` и `highlightableContent` самого сообщения. Поэтому найденный документ - сообщение, и клиентский поиск по чату не менялся. Апплеты подгружаются, только если у сообщения `applets > 0`, а сообщение переиндексируется, когда меняется этот счётчик. В текст сообщения идут только строковые и markup-атрибуты апплета. Сам `Poll` тоже становится документом индекса (`attachedTo` проиндексирован), но в поиск по чату не попадает: тот ищет только классы сообщений. - server/indexer/src/indexer/indexer.ts, models/server-chunter/src/index.ts.
- **Удаление.** `Poll` удаляется вместе с сообщением общим каскадом коллекций, а `PollAnswer` - триггером `OnPollRemoved`, в том числе при отдельном удалении опроса. Снимки в inbox обновляются по апдейту счётчика `applets`. - server-plugins/activity-resources/src/index.ts.

### Жалобы

- **Опция воркспейса, по умолчанию выключена.** `core.class.Configuration` с id `chunter.ids.ContentReportsConfiguration`: нет документа или `enabled: false` - жалоб нет. Переключатель "Жалобы" в Настройки -> Общее виден только владельцу - plugins/setting-resources/src/components/General.svelte; писать в `DOMAIN_CONFIGURATION` может только владелец (`ConfigurationMiddleware`).
- **Действие "Пожаловаться".** На чужом сообщении в канале (в DM - только на пользователя) и на пользователе; владельцам не показывается. - `canReportMessage`/`canReportPerson`, plugins/chunter-resources/src/report.ts; actions в models/chunter/src/actions.ts.
- **Доставка владельцам.** Клиент создаёт транзиентный `ContentReportAction` в своём PersonSpace; `ChunterMiddleware.onReportAction` отвечает `Forbidden`, если опция выключена или PersonSpace чужой; триггер `OnContentReport` кладёт карточку (`ActivityInfoMessage` с `chunter.string.ContentReport`) в DM каждого владельца с системой, кроме автора жалобы. Владелец, на которого пожаловались, карточку не получает, если её получит кто-то ещё; единственному владельцу она приходит всё равно (`ownersToNotify`). Создать или изменить такую карточку пользователь не может - `onInfoMessage`. - server-plugins/chunter/src/middleware.ts, server-plugins/chunter-resources/src/{report,reportCard}.ts.

### Производительность

- **Server-side агрегация activity.** При частых обновлениях markup storage объединяет `DocUpdateMessage` в окне `activityAggregationDelay` (по умолчанию 5 минут). - server/collaborator/src/storage/platform.ts.
- **Локальные патчи вместо рефетча.** `ChatViewport.handleTransactions` применяет Tx к загруженным сообщениям; рефетч только при конфликте `modifiedOn`. - plugins/chunter-resources/src/chatViewport.ts.
- **Кэш вьюпортов и отложенная activity-группа.** "Как работает" п.7-8.
- **Защита поиска от гонки и дублей.** `generation`, `appendUnique`. - plugins/chunter-resources/src/search/store.ts.
- **Кэш `hiddenChats` в middleware.** In-memory Map с ленивой подгрузкой из low-level storage. - server-plugins/chunter/src/middleware.ts.
- **Таблицы апплетов.** У `applet` (опросы) и `poll_answer` (ответы) свои схемы в `schemas.ts`. Индекс `("workspaceId", "attachedTo")` у `applet` нужен lookup `applets`, который идёт к каждому сообщению страницы чата. Индекс `("workspaceId", "attachedTo", space)` у `poll_answer` нужен запросу своего ответа (`PollPresenter`, сервис activity). Индекс не уникальный: нарушение уникальности уронило бы голос, и сервис activity повторял бы его бесконечно. Таблицы со схемой и индексами адаптер создаёт при старте, миграции не нужны. - foundations/server/packages/postgres/src/schemas.ts.

## Настройки и конфигурация

- `NotificationAppearancePreference.showChatBadge` - маркер на иконке чата.
- `DocNotificationSetting.mode` - режим канала (all/mentions/mute).
- `chunter.ids.ContentReportsConfiguration` - жалобы на сообщения и пользователей, по умолчанию выключены (см. "Жалобы").
- Константы клиента: `limit=50`, `MAX_CACHE_SIZE=10`, `TTL_MS=15 мин` (chatViewport.ts); дебаунс чтения 500 мс (scroll.ts); `loadMoreThreshold=200`, `newSeparatorOffset=150`, `forceReadPauseMs=3000` (ReverseChannelScrollView.svelte); `SUMMARY_TIMEOUT_MS=3 мин` (stores.ts).
- Ключ HMAC ответа викторины выводится из секрета токенов (`SERVER_SECRET` у transactor, `SECRET` у activity, значение одно). Смена секрета делает уже созданные викторины нерешаемыми: сервис не найдёт правильный вариант по старому хешу.
- Константы сервера: `updateChatInfoDelay=24 ч`, `hideDelay=14 дней`, `syncChatCoalesceMs=60 с` (server-plugins/chunter-resources/src/index.ts).
