# Penpot -> код макетов

Макеты живут кодом в `dev/penpot/`. Penpot - место, где человек показывает, что и где поменять: правит фигуры руками или оставляет комментарий. Этот навык переносит такие правки в скрипты. Общая схема и команды - `docs/penpot.md`, особенности Penpot - `docs/memory/penpot.md`.

## Кто делает работу

Основной контекст дорогой: скриншоты, DOM-замеры, JSON `diff` и вывод сборки его быстро забивают. Поэтому:

- Тяжёлые шаги выполняют субагенты Sonnet (`Agent`, `model: "sonnet"`):
  - сбор и разбор `design:diff`;
  - замер стенда (DOM, стили, иконки);
  - правка скриптов `dev/penpot`;
  - сборка;
  - экспорт и сравнение скриншотов.
- Агент получает самодостаточный промпт: файл Penpot, страницу, пути скриптов, что проверить. Возвращает таблицу "что -> где изменено", не скриншоты и не сырые дампы.
- Независимые части запускать параллельно: разные экраны, разные комментарии.
- Основная модель только решает: что менять в компоненте, а что в экране, что спросить у человека. Затем проверяет итог по короткому отчёту агента.
- Одна вкладка Penpot на MCP-ключ: параллельные агенты не должны одновременно собирать разные файлы. Сборки идут последовательно, правки скриптов - параллельно.

## 0. Подготовка

- `pnpm -w design` - Penpot поднят, файл существует.
- Нужный файл открыт в одной вкладке, кнопка MCP показывает "MCP connected", вкладка активна. Заморожена (ошибка "suspended") - попросить человека кликнуть по вкладке. Самому не переоткрывать: в ней могут быть несохранённые правки.

## 1. Снять расхождения

```bash
pnpm -w design:diff
```

Печатает список и пишет `dev/penpot/files/diff/<файл>.json`. Каждая запись содержит `page`, `path` (имена фигур от фрейма), `src` (скрипты, которые рисовали страницу) и `kind`:

| kind | Что значит | Куда переносить |
|---|---|---|
| `comment` | Просьба словами, привязана к фрейму (`path`) | Сделать, что просят; ответить в треде (шаг 4) |
| `changed` | Изменились свойства: `c` текст, `f` заливка, `s` обводка, `l` раскладка (dir, gap, padding, align), `wh` размер, `r` скругление, `fs`/`fw` шрифт, `xy` позиция, `h` скрыта | Данные или параметр вызова в скрипте из `src` |
| `added` | Новая фигура (поля `structure`, `css`) | Новый вызов kit или новый компонент kit |
| `removed-children` | Человек удалил дочерние фигуры | Убрать из данных или вызова |
| `page-added` | Страница, нарисованная вручную целиком | Новый скрипт экрана и строка в `design.json` |

Для цветов `diff` подсказывает токен (`token: theme-...`). `no token` - цвета нет в теме.

## 2. Решить, где менять

- По `path` и `src` найти место в скрипте: имена фигур совпадают с именами в коде (`IssueCard IST-152`, `ColumnHeader Code Review`, `Settings content`).
- Фигура внутри компонента kit (`IssueCard`, `ColumnHeader`, `Button/...`, `NavItem/...`):
  - Правка только этого экземпляра (текст, данные) - менять данные в скрипте экрана.
  - Правка вида (цвет, отступ, шрифт) - это изменение компонента везде, а значит и в продукте. Спросить человека: менять компонент kit (затронет все экраны и библиотеку) или это частный случай экрана.
- Цвет только через `T('<токен>')` или палитру, размер через `D()`. `no token` - не вписывать hex молча: спросить, добавлять ли цвет в тему (`packages/theme`) или взять ближайший токен.
- Новый переиспользуемый элемент - функция в `kit/` и запись в `groups` в `library/ui-kit.js`. Правило согласования с `@hcengineering/ui/kit` - в плане `foundation-tasks/docs/ux/2026-10-22-penpot-ui-kit.md`: новый компонент сначала `Proposed`.
- Комментарий может просить изменение продукта, а не только макета. Такое записать отдельным пунктом для `design-implement`.

## 3. Пересобрать и проверить

```bash
pnpm -w design:build "<файл>" --force
pnpm -w design:diff
```

- `--force` нужен, потому что расхождения ещё числятся. Пересборку запускать только после того, как каждая запись из шага 1 перенесена или явно отложена человеком: пересборка стирает ручные правки (снимок сохраняется в `dev/penpot/files/backup-*`).
- Сборка идёт в открытой вкладке, если подключён именно этот файл.
- После сборки `diff` должен показать 0 правок. Остаться могут только комментарии. Что-то осталось - разобрать, почему код рисует не то, и повторить.
- Изменился компонент kit - пересобрать и UI Kit, `pnpm -w design:up`: он пересоберёт все файлы, где изменился хеш исходников.

## 4. Закрыть комментарии

На каждый перенесённый комментарий ответить в треде, что сделано и где, и закрыть его:

```bash
node dev/penpot/penpot.mjs reply "<файл>" <номер треда> "Перенесено: dev/design/screens/<...>.js"
```

Комментарии читаются и закрываются через RPC бэкенда. API комментариев плагина (`findCommentThreads`) не использовать: на нём вкладка редактора зависала.

## 5. Отчёт

Таблица: правка из Penpot -> файл и что изменено. Отдельно - что отложено и почему, и пункты, которые требуют изменения продукта. Не коммитить без просьбы.
