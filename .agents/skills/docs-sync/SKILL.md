# Документация: карта и сверка

Карта - раздел `## Пользовательская документация` в каждом `docs/features/<area>.md`, формат и
статусы - в `docs/features/README.md` (раздел "Пользовательская документация"). Документация -
`../platform-docs` (другой путь - `DOCS_REPO`), Astro Starlight, страницы
`src/content/docs/{ru,en}/<раздел>/<страница>.mdx`, сайдбар руками в `astro.config.mjs`.

Скриншоты и видео - скилл `docs-media`.

## Роли

| Работа | Роль | Параллельно | Что отдаёт |
|---|---|---|---|
| Поиск: выписать утверждения страниц, найти кандидатов в коде, тексты `lang/*.json`, коммиты | сборщик фактов | до 5 | только ссылки: `file:line` и цитаты; не сравнивает, не решает "найдено/расходится/видит ли пользователь" |
| Сверка: сравнить страницу с кодом, решить статус, найти недостающее | исполнитель | до 2 | статусы и расхождения с доказательством `file:line` |
| Правки: строки карты, страницы, сайдбар | исполнитель | (те же 2), файлы не пересекаются | дифф и список утверждений, на которые опирался |
| Финальная проверка | проверяющий | 1, новый независимый проверяющий на каждый круг | вердикт по каждому утверждению и строке, с `file:line` |

- Основной поток раздаёт работу через доступный инструмент делегирования, спрашивает пользователя и сводит итог. При делегировании код и страницы сам не читает - только ответы исполнителей.
- Лимиты - на весь скилл: в задании писать "своих под-агентов не запускай", иначе лимит теряется.
- Задание самодостаточное: абсолютные пути к foundation и platform-docs, область, файлы,
  формат ответа. Исполнитель не видит этот разговор.
- Проверяющий получает только дифф и пути к коду - не историю сессии и не ответы сборщика фактов и исполнителя.
- Замечания проверяющего - тому же исполнителю на правку, затем новый проверяющий. Два круга без согласия -
  вынести пользователю список спорных пунктов.
- Если делегирование недоступно, выполнять этапы последовательно и прямо указать, что независимой проверки не было.

## Перед началом

```bash
git -C ../platform-docs status --short && git -C ../platform-docs branch --show-current
git describe --tags --abbrev=0        # версия для колонки "Сверено", без v
```

platform-docs с чужими незакоммиченными правками - спросить пользователя, прежде чем писать туда.

Строки `off` (функционал выключен или решено не документировать) все режимы пропускают; `plan` с
"отложено" в "Расхождении" - не брать в `write`, пока пользователь не скажет.

## Режимы

### `map [область]`

Построить или обновить таблицу области (без области - все 16, волнами по 5).

1. Сборщик фактов на область:
   > Прочитай `<foundation>/docs/features/<area>.md`, раздел `## Фичи`. По каждому пункту (жирный
   > заголовок): заголовок дословно, строка в файле, символы и файлы из пункта. Затем grep по
   > `<platform-docs>/src/content/docs/ru` и `/en` по ключевым словам пункта и по UI-текстам из
   > `lang/ru.json` пакетов из раздела "Где код". Ответ - таблица: фича | строка | grep-попадания
   > на страницах (`file:line` и цитата). Не решай, видна ли фича и про неё ли страница.
2. Исполнитель сверяет попадания: какая страница действительно про фичу, видит ли её пользователь.
   Исполнитель (до 2, области не пересекаются) пишет раздел `## Пользовательская документация` после
   `## Фичи`. Существующие строки не теряются: `ok` со старой версией "Сверено" остаётся `ok`,
   статус без сверки ставится только новым строкам - `partial` (страница есть, не сверена),
   `plan`, `no-en`, `internal`.
3. Полнота: раздел "Фичи" писался для разработчика и пропускает пользовательское. Две проверки:
   - страницы без строки в карте:
     ```bash
     find ../platform-docs/src/content/docs/ru -name '*.mdx'   # минус пути из колонок ru всех карт
     ```
     по каждой сборщик фактов выписывает утверждения и grep-кандидатов в коде (`file:line`);
   - интерфейс без пункта в "Фичах": сборщик фактов по моделям области (`models/<x>/src`) выписывает
     приложения, разделы навигатора, действия, настройки, виды, диалоги создания (тексты из
     `lang/ru.json`, `file:line`); есть ли пункт в "Фичах" - решает исполнитель.
   Найденное исполнитель добавляет в "Фичи" (с файлами и символами, как соседние пункты) и строкой в
   карту. Страницы, которым нет области, - новая область в `docs/features/` и строка в `README.md`.
4. Сверка количества - строк в карте ровно столько, сколько пунктов в "Фичах" (жирные заголовки).
5. Проверяющий: каждая строка - фича есть в "Фичах", страница существует и говорит об этой фиче, статус
   не завышен (`ok` без сверки - ошибка), найденное в п. 3 не пропущено.

### `since <tag>`

Найти фичи, изменённые после тега, которые PR не пометил сам.

1. `git log --no-merges --pretty='%h %s' <tag>..HEAD` - разбить на до 5 частей, сборщик фактов на часть:
   > Для каждого коммита: `git show --stat` и дифф `lang/*.json`, `*.svelte`, `models/*`. Ответ:
   > коммит | затронутые пакеты | область (по таблицам "Где код" в `docs/features/*.md`) |
   > что изменилось на экране - цитата из диффа (тексты, кнопки, поля) или "на экране ничего".
2. Исполнитель переводит строки затронутых фич в `stale` с причиной (номер задачи из заголовка
   коммита); новая пользовательская фича без строки - `plan`.
3. Проверяющий проверяет каждую изменённую строку по коммиту.
4. Пользователю - список страниц к правке, по `stale` и `plan`.

### `verify <область|страница>`

1. Сборщик фактов на страницу (до 5):
   > Выпиши из `<страница>.mdx` каждое проверяемое утверждение: кнопка, пункт меню, поле, шаг,
   > настройка, ограничение - с номером строки и цитатой. Для каждого дай кандидатов из кода:
   > grep ключевых слов по `plugins/*-assets/lang/{ru,en}.json` (все пакеты) - ключ, текст,
   > `file:line`; grep ключа по `plugins/*/src`, `models/*/src` - `file:line`. Совпадает ли
   > текст и верно ли утверждение - не решай. Скриншоты страницы - перечислить пути.
2. Исполнитель сверяет: по кандидатам сборщика фактов и сам по коду/стенду решает, верно ли каждое утверждение,
   ищет пропущенное; статус строки - `ok` и версия, или `stale`/`partial` с одной фразой в
   "Расхождение"; правки страниц - списком с доказательством. Страницу на этом шаге не правит.
3. Проверяющий финально проверяет каждую строку `ok`/`stale`/`partial` и каждую правку.

### `write <фича>`

Написать страницу или дописать существующую. Берётся строка `plan`, `stale` или `partial`.

1. Сборщик фактов (до 5) собирает факты фичи: путь пользователя от входа до результата (компоненты, `data-id`,
   тексты кнопок из `lang/ru.json` и `lang/en.json`), настройки, ограничения, права. Источник - раздел
   фичи в `docs/features/<area>.md` и код по его ссылкам.
2. Спросить пользователя доступным инструментом вопросов: нужен ли en; нужны ли скриншоты/видео (тогда после
   текста - `docs-media`).
3. Исполнитель пишет страницу (правила ниже), пункт сайдбара, строку карты -> `ok` и версия.
4. Проверяющий сверяет каждое утверждение страницы с кодом, проверяет сайдбар и ссылки.
5. Сборка: `cd ../platform-docs && pnpm build` (`astro check` + `astro build`) - битый импорт
   картинки или разметка MDX валят её. `test:links` не запускать: он ждёт сайт на 8080, где живёт
   dev-стенд платформы.

Временные скрипты агентов (Playwright-пробы стенда) - только в `.tmp-shots/` (в `.gitignore`), Playwright
- по абсолютному пути `require('<foundation>/tests/sanity/node_modules/@playwright/test')`: файлы в `tests/sanity`
попадают в коммиты пользователя.

## Страница

- Правленую страницу сверять целиком, каждое утверждение, а не только строки из списка правок: точечная
  правка оставляет соседние ошибки (FUSIO-38, выключенный функционал, видео и ссылки апстрима) и вносит новые.
  Финальный проверяющий тоже проверяет всю страницу.

- Шапка `title`, `description`; ru и en - одинаковое имя файла в своих папках.
- Пишем то, что видит пользователь: шаги, названия кнопок и полей дословно из `lang/*.json`, зачем
  это нужно. Без имён классов, пакетов и файлов кода.
- Продукт - "Интабия Платформа" (en - Intabia Platform). Апстрим (форк `hcengineering/platform`)
  не упоминается: ни имени, ни ссылок на его сайт, сообщество, соцсети и ботов, ни его брендинга на
  картинках. Встретил на правленой странице - убрать, замену контактов спросить у пользователя. Стиль, тон и разметка - как у соседних
  страниц раздела; правка существующей страницы - по расхождению с кодом, чужие формулировки без
  причины не переписываются.
- Картинки - импорт из `src/assets/screenshots/...` и `<a href={x.src}><Image src={x} alt="..." inferSize /></a>`,
  видео - `<LocalVideo id="..."/>` (`src/components/LocalVideo.astro`).
- Ссылки на другие страницы - `/<раздел>/<страница>/`, без языка.
- Новая страница - пункт в `sidebar` `astro.config.mjs`: `label` (ru), `translations: { en: ... }`,
  `link`.

## Просмотр

en-локаль на сайте не публикуется; локально её включает `DOCS_EN=1`:
`cd ../platform-docs && DOCS_EN=1 pnpm dev --port 4321` - страницы `http://localhost:4321/docs/{ru,en}/<путь>/`.

## Итог

- Правки страниц, картинки и сайдбар - сразу в рабочее дерево `platform-docs`, без коммита и без
  промежуточных списков: пользователь смотрит `git diff` и коммитит фазу одним коммитом. Карта - так же
  в рабочее дерево foundation.

- Пользователю: что сверено, что `stale`/`plan`, какие страницы правлены, вердикты проверяющего или отсутствие независимой проверки.
- Две ветки правок: foundation (карта) и platform-docs (страницы). Коммиты - только по просьбе.
